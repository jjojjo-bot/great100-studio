# Great100 Studio의 REA 역공학 적용 계획

현재 운영 기준은 **ChatGPT Plus만 사용하며 OpenAI API 키를 요구하지 않는 제작 흐름**이다. G1의 API 자동 음성 생성 UI는 기본 숨김으로 보관한다. 현재는 내레이션 대본 복사·직접 녹음·외부 오디오 업로드·시간 조정·출력을 사용하며, API 도입은 나중에 명시적으로 선택할 때 활성화한다. Plus의 별도 승인된 Responses API 연동은 이번 Chat Completions 음성 경로와 구분한다([공식 연동 범위](https://developers.openai.com/siwc/quickstart), [음성 생성 API](https://developers.openai.com/api/docs/guides/audio-chat-completions)).

2026년 10월 20일 작성. [서비스 선정 조사](rea-service-selection-2026-10-20.md)와 [REA 검증 기록](rea-service-evidence-2026-10-20.json)을 바탕으로 작업 범위와 완료 기준을 정리했다. A 기준 이미지 처리와 B 편집 이력은 구현·검증을 완료했다. [첫 적용 결과](rea-first-release-2026-10-20.md)에 실제 검증 범위와 남은 한계를 기록했다. C 편집 검증·형식 호환, D 공통 시간 계산·내레이션 길이 연동, E 자료 목록·구간 구성, F1 순서 변경·F2 나누기·F3 인접 장면 합치기, G1 장면별 음성 생성 연결, H1 전체 장면 작업 보드, H2 이미지 일괄 배치·H3 후보 이미지 비교·H4 이미지 원본 보관함·H5 출력 전 자료 점검·H6 장면 이미지 프롬프트 묶음·H7 내레이션 파일 일괄 배치·H8 내레이션 대본 묶음 내보내기는 아래 구현 결과를 참고한다. G1은 현재 기본 숨김이다. 실제 한국어 품질 평가, G2 발화 정렬과 H8 이후 확장 작업은 후속 범위다.

**첫 적용 묶음은 업로드한 인물 기준 이미지의 참조 전달과 편집 실행 취소로 잡는다.** Vrew에서는 자막·클립·편집 명령의 동작을 분석하고, Great100에는 작은 변경부터 적용한다. 이후 시간 연동을 정리한 뒤 장면 나누기·합치기, 내레이션 자동화, 전체 장면 검토와 일괄 생성으로 확장한다.

| 단계 | 역공학에서 확인할 내용 | Great100에 적용할 결과 | 선행 조건과 완료 기준 |
| --- | --- | --- | --- |
| 0 | Vrew의 자막 편집, 클립 시간, 실행 취소, 장면 조작 | 동작 비교표와 편집 데이터·명령 연결표 | 확보한 코드의 근거와 실제 동작을 구분한다. 미확인 동작은 Great100의 설계 선택으로 명시한다. |
| 1 | 인물 참조가 장면 지시와 연결되는 과정은 Mootion을 보조로 참고 | 업로드·생성한 기준 이미지를 장면·썸네일 생성에 일관되게 사용 | 이미지 원본을 읽어 유효한 참조 데이터로 변환하고 저장 모드별로 검증한다. 이 변경은 Great100 코드 근거만으로도 착수할 수 있다. |

| 3 | 문장·자막·장면의 시간 관계 | 음성 길이에 맞춘 장면 조정, 공통 시간 계산, 편집용 검증 | 원본 제작안과 편집 상태를 구분하고 미리보기·출력의 시간 계산을 통일한다. |

| 6 | Mootion의 전체 장면 검토와 선택적 재생성 | 장면 보드, 미선택·오류 필터, 생성 결과 비교와 부분 재시도 | 단계 2의 편집 처리와 단계 4의 자료 참조 구조를 재사용한다. |

첫 배포 범위는 **단계 1과 2**다. 단계 0은 구현 판단에 필요한 조사 범위를 한정한다. 단계 3 이후에는 프로젝트 데이터와 출력 동작에 대한 변화가 커지므로 각각 독립된 작업으로 검증한다.

**현재 구조에서 먼저 해결해야 할 연결 관계가 있다.** 단순한 UI 추가로 처리하면 다음 문제가 생긴다.

| 코드에서 확인한 사실 | 구현에 주는 제약 |
| --- | --- |
| 장면·썸네일 생성이 `mode === "openai"`인 기준 이미지만 전달한다. | 업로드 이미지도 실제 원본을 읽는 공통 경로가 필요하다. URL을 그대로 API에 보내는 방식으로는 해결되지 않는다. |
| `persist`가 오래된 콜백의 변경을 `mergeProjectChanges`로 병합한다. | 실행 취소도 최신 상태에 특정 필드의 역변경을 적용해야 한다. 과거 프로젝트 전체를 복구하면 새로 완료된 업로드를 잃을 수 있다. |
| ID가 있는 배열의 병합은 현재 배열의 순서를 유지한다. | 장면 재정렬에는 순서를 명시적으로 바꾸는 연산이 필요하다. 배열 순서만 바꿔 기존 저장 함수에 넣는 접근은 부족하다. |
| APP_DATA 검증이 `scene_01` 형식의 ID·순서와 핵심 업적의 장면 연결을 요구한다. | 원본 입력 검증과 편집된 프로젝트 검증을 분리해야 자유로운 분할·병합이 가능하다. |
| 자막에는 안정적인 ID가 없고 시간은 본문 기준 절대 초다. | 초기 이력은 장면 ID와 자막 배열 단위로 기록한다. 구조 편집 도입 전에는 자막에도 안정적인 ID가 필요하다. |
| Tauri의 녹음·동영상 읽기가 장면 번호를 경로로 사용한다. | 표시 순서와 저장 위치를 분리해야 장면 이동 후에도 같은 원본을 읽는다. |
| 클라우드는 저장 후 더 이상 참조되지 않는 파일을 제거한다. | 장면을 제거하거나 합칠 때 실행 취소가 필요한 원본을 유지하는 자료 목록이 필요하다. |
| 한 장면의 녹음은 파일 하나이며 화면도 제한된 조합을 사용한다. | 두 장면을 합치려면 이미지·영상·음성의 내부 구간을 보존할 수 있어야 한다. |
| 완성 MP4는 프로젝트 수정 시각과 렌더 버전으로 유효성을 판단한다. | 실행 취소·시간 변경도 새 편집으로 저장하고 출력 갱신 상태에 반영해야 한다. |

**단계 0에서는 기능별로 답이 필요한 질문만 추적한다.** 이미 확보한 Vrew JS 3개와 기존 Evidence를 먼저 사용한다. 같은 자료의 전체 분석을 반복하기보다 관련 모듈·소스 위치를 조회하고, 부족한 직접 의존성만 추가 확보한다. 파일이 바뀌면 기존 SHA-256과 구분해 다른 자료 묶음으로 기록한다.

| 조사 질문 | 관찰할 행동 | 남길 결과 |
| --- | --- | --- |
| 문구와 내레이션은 어떻게 연결되는가? | 자막 한 줄 또는 대본 한 문장을 수정한다. | 바뀐 필드, 음성 재생성 여부, 다른 자막·장면에 미치는 영향 |
| 자막 경계의 시간 규칙은 무엇인가? | 시작·종료 손잡이를 이동하고 인접 자막에 접근한다. | 최소 길이, 겹침 처리, 시간 단위, 재생 위치 변화 |
| 실행 취소 한 번의 단위는 무엇인가? | 한 번 드래그, 연속 타이핑, 후보 변경 후 실행 취소한다. | 묶음 기준과 다시 실행 상태 |
| 비동기 결과는 어떻게 보존되는가? | 생성·업로드가 진행되는 동안 다른 편집을 한다. | 늦게 도착한 결과와 사용자 편집의 병합 방식 |
| 장면 경계를 바꾸면 무엇이 이동하는가? | 순서 변경, 자막 경계에서 분할, 인접 장면 병합을 한다. | ID, 자료 참조, 음성 구간, 자막·재생 위치의 변화 |
| 참조 이미지와 촬영 지시는 어떻게 구분되는가? | 같은 인물 참조에 다른 구도·장소를 지정한다. | UI 설정과 관찰 가능한 요청 필드·결과의 관계 |

각 결과는 행동 이전 상태, 행동, 이후 상태, 근거 소스 위치 또는 Evidence ID, 적용할 Great100 규칙으로 연결한다. 정적 코드의 후보 경로와 런타임 결과를 별도로 표시한다. 이번 표본에서 확인된 `mergeClips`, `undoAction`, `redoAction` 등은 조사 진입점이며 구현 규칙이 확인된 상태는 아니다.

런타임은 사용할 수 있는 브라우저의 해당 체험판이나 공식 앱으로 관찰한다. 계정·생성 한도 등으로 관찰이 어려운 질문은 미확인으로 남기고, Great100에서 필요한 동작을 명시해 자체 테스트한다. 조사 산출물은 여섯 질문에 대한 동작표와 다음 구현에 필요한 데이터·명령 연결표다. 서버의 생성 모델을 복원하는 작업은 이 계획의 구현 의존성이 아니다.

**단계 1은 기준 이미지 원본을 읽는 경로를 통일한다.** `mode` 대신 선택한 후보의 종류와 실제 자료를 기준으로 참조 가능 여부를 판단한다. 업로드 이미지와 생성 이미지를 모두 처리하며, mock SVG는 생성 참조 대상에서 제외한다.

새 공통 함수 `resolveReferenceImage(project, candidate)`를 제안한다. R2의 저장 키, IndexedDB 자료, 데스크톱 파일, 아직 저장 중인 data URL 등 현재 저장 상태에 맞게 원본을 읽고, 지원되는 PNG·JPEG·WebP의 base64 데이터로 변환한다. 웹 API의 기존 3MB 참조 제한과 전체 요청 크기를 고려해 참조용 사본을 축소·압축한다. 프로젝트에 보관한 원본은 유지한다.

이 함수를 장면과 썸네일 생성에 연결한다. 보조 이미지에는 인물이 등장하지 않을 수도 있으므로, 기준 이미지 적용은 사용자가 고를 수 있게 다음 UI 작업에서 다룬다. 참조 원본을 읽지 못했으면 생성 요청 전에 재시도 가능한 오류를 표시한다.

변경 예상 위치는 `App.tsx`, `platform.ts`, 새 `reference-image.ts`, `api/generate.ts`, 필요한 Tauri 파일 읽기·요청 검증이다. 완료 기준은 다음과 같다.

- 업로드·생성한 기준 이미지가 같은 참조 전달 경로를 사용한다.
- 로컬 웹과 계정 저장에서 새로고침 후에도 선택한 참조를 읽는다.
- 장면·썸네일 요청에 실제 이미지 데이터가 포함되고 MIME·크기 제한을 만족한다.
- 형식 오류, 과도한 크기, 원본 읽기 실패가 생성 요청 전에 처리된다.
- 모의 응답으로 요청 형식을 확인하고, 실제 이미지 일관성은 동일한 참조와 서로 다른 구도의 소수 장면으로 별도 평가한다.

**단계 2는 편집 명령과 저장을 연결한다.** 우선 지원할 동작은 자막 문구·시간, 자막 시간 초기화, 후보 선택, 장면 프롬프트, 이미지 효과, 음악 볼륨, 현재 제공하는 화면 전환·트림 설정이다.

새 `editor-commands.ts`와 `useEditorHistory.ts`를 제안한다. 명령에는 프로젝트 ID, 장면·자료 ID, 대상 필드, 변경 전후 값과 묶음 ID를 담는다. 실행 취소는 최신 프로젝트에서 해당 필드만 역변경한다. 대상이 남아 있고 현재 값이 명령의 적용 후 값과 일치하는지 검사해, 같은 필드에 도착한 다른 변경을 덮어쓰지 않게 한다. 저장 버전, 서명 URL, 생성 중 상태 등은 사용자 편집 이력과 분리한다. 명령 적용 결과를 기존 저장 큐와 충돌 처리로 전달한다.

첫 구현의 이력은 프로젝트를 열어 둔 동안 최근 50개 편집 묶음으로 제한한다. 같은 프로젝트의 제작 단계 이동은 이력을 유지하고, 다른 프로젝트를 열거나 서버의 최신 작업으로 교체하면 초기화한다. 한 번의 드래그는 한 묶음으로 기록한다. 연속 타이핑은 같은 입력란에서 묶되 한글 IME 조합 완료를 고려한다. 실행 취소 후 새 편집을 하면 다시 실행 목록은 비운다.

입력란 내부에서는 브라우저의 텍스트 실행 취소를 사용할 수 있게 전역 단축키를 가로채지 않는다. 도구 모음의 실행 취소 버튼과 입력란 밖의 단축키로 프로젝트 편집을 되돌린다. 버튼에는 다음에 되돌릴 편집 이름을 표시한다.

후보 생성·업로드 완료는 시스템 결과로 반영하므로 자막 실행 취소에 휩쓸리지 않아야 한다. 파일을 실제 삭제하는 동작은 첫 이력 범위에 넣지 않는다. 삭제된 자료를 참조하는 이전 이력은 무효화하고 안내해, 실행 취소가 존재하지 않는 파일을 선택하지 않게 한다. 저장 실패 시 편집본과 이력은 유지하고 실패 상태를 보여 주며, 다른 PC의 버전 충돌 시에는 기존 최신 작업 복구 절차를 따른다.

완료 기준은 자막 드래그 한 번이 정확히 한 번에 복구되고, 이미지 생성 완료 이후 자막을 되돌려도 생성 후보가 남으며, 빠른 편집·실행 취소가 클라우드 저장 순서를 깨뜨리지 않는 것이다. 기존 [병합 테스트](../../src/project-changes.test.ts)와 [클라우드 저장 테스트](../../src/cloud.test.ts)에 이 경쟁 상황을 추가한다.

**단계 3은 편집 시간의 기준을 통일한다.** 원본 `source_text`와 `source`는 제작안으로 보관하고, 현재 프로젝트의 순서·문구·시간·자료 참조를 편집 상태로 검증한다. 입력 시의 `validateAppData` 규칙과 출력 가능한 편집 상태의 규칙을 분리한다. 핵심 업적의 시각화와 자막 내용 검사는 편집 후에도 이어가되, 원본 장면 ID의 형식이 편집 기능을 막지 않게 한다.

추가 메타데이터에는 독립적인 `editor_version`을 둔다. APP_DATA의 `schema_version`과 구분해 기존 1·2.0·2.1 프로젝트를 읽는다. 원본 프로젝트 ID는 장면 순서 변경 때문에 재발급하지 않는다. 표시 번호는 순서에서 계산하고, 자막 ID·원본 장면 연결·핵심 업적의 현재 장면 연결을 편집용으로 관리한다.

새 `timeline.ts`는 장면 길이와 자막의 장면 내 상대 시간을 기준으로 계산한다. 내부 계산은 정수 밀리초를 사용하고, 현재 초 단위 필드와는 어댑터로 변환한다. 편집 작업이 확정될 때 뒤 장면의 시작·종료와 절대 자막 시간을 함께 갱신한다. 별도의 절대 시간과 상대 시간을 각각 수정 가능한 원본으로 저장하지 않는다.

기존 프로젝트를 변환할 때는 현재 렌더러가 실제 사용하는 장면 순서·길이와 자막의 장면 내 위치를 보존한다. 원문에 시간 틈이 있던 프로젝트도 변환 전후 미리보기·출력 비교에 포함하고, 원문의 절대 시각은 `source`에 유지한다. 시간 계산을 바꾸는 변환은 수정 전 JSON·자료 백업을 남긴다.

처음 제공할 시간 연동은 **내레이션 길이에 맞추기**다. 현재 업로드 함수는 장면보다 긴 녹음을 거부하므로, 오디오 길이 검사와 파일 저장을 분리해 길이를 읽은 뒤 장면 조정안을 먼저 보여 준다. 읽은 오디오 길이를 수용하도록 장면 길이를 0.1초 단위로 올림하고 기존 1~120초 범위를 검사한다. 기존 자막 시간을 유지할지 비율대로 재배치할지 적용 전에 보여 준다. 자막의 최소 길이·순서·장면 경계가 성립하지 않으면 적용하지 않는다. 이 재배치는 편집 편의 기능이며 실제 단어 타이밍을 인식한 정렬로 표시하지 않는다.

미리보기와 MP4는 같은 시간 계획을 사용한다. 프레임 경계 보정은 공통 함수에서 수행해 장면마다 반올림 오차가 누적되지 않도록 하고, 자막·화면·음성의 주요 경계 차이는 15fps 기준 한 프레임 이내를 완료 기준으로 잡는다. 3초 오프닝과 엔딩의 시간도 같은 검사에 포함한다.

추가 필드가 포함된 프로젝트의 구버전 저장은 자료를 잃을 수 있다. 클라우드 저장 계약에 편집 형식 버전 검사를 포함하고, 기존 파일은 변환 전 사본으로 복구할 수 있게 한다. JSONB 저장·Tauri 직렬화·ZIP 출력이 새 필드를 유지하는지도 검증한다. 필요한 SQL 변경은 이 단계의 호환성 작업에 한정한다.

**단계 4는 자료 ID와 구간 표현을 먼저 도입한 뒤 장면 조작을 연다.** 프로젝트 자료 목록은 원본의 안정적인 ID, 저장 키 또는 실제 경로, 형식·길이를 보관한다. 장면은 그 자료를 참조한다. Tauri는 바뀌는 표시 번호 대신 자료의 저장 위치를 읽도록 바꾸고 기존 번호 기반 폴더는 읽기 호환 경로로 남긴다. ZIP 폴더 이름은 내보내는 시점의 표시 순서로 만들 수 있다.

영상과 음성에는 원본의 시작·종료 구간과 장면 안의 배치 시간을 표현한다. 기존의 주 이미지·동영상·보조 이미지·단일 녹음도 이 공통 구성으로 변환한다. 미리보기와 렌더러가 같은 구간 구성을 읽도록 한 뒤 다음 순서로 제공한다.

1. 순서 변경은 장면 ID·자료·녹음 연결을 유지한 채 표시 번호와 시간을 다시 계산한다.
2. 나누기는 먼저 자막 사이 경계에서 지원한다. 화면과 음성은 원본을 공유하고 사용할 구간만 나눈다.
3. 인접 장면 합치기는 두 장면의 내부 화면 전환과 음성 구간을 순서대로 보존한다. 자막 위치도 새 장면 기준으로 옮긴다.

각 구조 변경은 하나의 실행 취소 단위다. 핵심 업적이 포함된 장면의 연결과 원본 장면의 출처 목록도 함께 갱신한다. 자료 목록은 현재 편집 상태와 실행 취소에 필요한 원본을 유지한다. 장면에서 참조가 사라졌다는 이유만으로 클라우드 파일을 즉시 제거하지 않도록 정리 규칙을 바꾼다.

완료 기준은 이미지·짧은 영상·보조 이미지·녹음이 섞인 프로젝트를 이동·분할·병합하고 되돌린 뒤에도 같은 원본을 읽고 저장·재열기·ZIP·MP4가 일치하는 것이다. 병합 시 두 번째 장면의 이미지나 녹음을 잃는 구현은 이 기준을 충족하지 않는다.

**단계 5의 TTS는 음성 생성과 자막 정렬을 각각 검증한다.** 공급자와 모델은 한국어 표본, 문장·단어 타임스탬프 제공 여부, 비용과 지연, 재시도 동작을 확인한 뒤 선택한다. 타임스탬프가 없으면 강제 정렬의 별도 가능성을 검증하고, 문자 길이 비례 배분은 추정 시간으로 구분한다.

첫 범위는 내레이션 생성·교체, 목소리·속도 선택, 변경한 장면만 재생성이다. 요청 시작 당시의 문구와 옵션을 식별값으로 저장해, 생성 중 문구가 바뀌면 오래된 음성이 현재 편집본을 덮어쓰지 않게 한다. 기존 녹음은 새 음성 생성·저장이 성공한 뒤 교체하고, 자막이나 대본을 바꿨을 때 기존 음성과 불일치를 표시한다. 재시도와 재생성은 각각의 사용량을 추적할 수 있어야 한다.

**단계 6은 전체 장면의 선택과 재시도를 빠르게 만든다.** 한 화면에서 장면의 선택 이미지·동영상, 자막 길이, 녹음 상태를 비교하고 미선택·실패·변경 필요 장면을 모아 본다. 일괄 생성은 장면별 작업 상태와 부분 성공을 저장하며, 실패한 장면만 다시 요청한다. 원래 후보와 새 결과를 함께 보관하고 사용자가 선택을 확정한다. 인물 참조와 구도·장소 지시는 분리해 같은 인물을 다른 장면으로 이어 갈 수 있게 한다.

실제 구현은 다음 작업 단위로 나누는 편이 검토하기 좋다. 각 단위에는 해당 동작의 검증과 회귀 확인을 포함한다.

| 작업 단위 | 주요 변경 예상 위치 | 검토할 핵심 |
| --- | --- | --- |
| A 기준 이미지 원본 처리 | 새 `reference-image.ts`, `platform.ts`, `App.tsx`, API·Tauri 관련 경로 | 저장 모드별 원본 읽기, 크기·형식, 장면·썸네일 연결 |

A는 자체 코드 근거로 먼저 구현할 수 있다. B는 단계 0에서 확인한 편집 행동을 반영한다. C → D → E → F의 순서로 장면 편집의 기반을 만든다. G는 C·D 이후, H는 B·E의 결과를 사용한다. 과금·대기 시간이 있는 생성 API는 모의 응답으로 일반 검증을 수행하고 실제 품질 확인용 표본과 구분한다.

검증 자료는 세 장면의 짧은 합성 프로젝트와 14~18장면의 대표 제작안으로 구성한다. 자막·녹음이 없는 장면, 짧은 동영상, 보조 이미지, 업로드한 인물 기준 이미지, 생성 중 다른 편집을 수행하는 상황을 포함한다. 기존 v1·2.0·2.1 프로젝트도 불러오기 회귀 자료로 사용하며, 2.0의 기존 출력 제한은 별도로 유지·검증한다.

| 검증 항목 | 통과 기준 |
| --- | --- |
| 이력 | 드래그 한 번은 이력 한 개다. 한글 입력과 다시 실행이 예상한 묶음으로 동작한다. |
| 비동기 작업 | 자막을 되돌려도 완료된 업로드가 남고, 오래된 생성 응답이 새 편집을 덮어쓰지 않는다. |
| 저장 | 로컬·계정 저장에서 새로 열었을 때 편집본이 일치한다. 계정 변경·버전 충돌의 기존 차단이 유지된다. |
| 시간 | 자막·영상·음성의 순서와 범위를 검증하고 주요 미리보기·출력 경계는 한 프레임 이내로 일치한다. |
| 장면 구조 | 재정렬·분할·병합 후에도 원본 자료·음성 구간과 핵심 업적 연결이 보존된다. |

| 저장 모드 | 로컬 웹·클라우드·Tauri의 자료 읽기와 쓰기를 각각 검증한다. 실제 실행하지 못한 플랫폼은 미검증으로 표시한다. |

코드 변경 시 관련 Vitest 테스트를 먼저 실행하고 `npm run typecheck`, `npm test`, `npm run build`로 확인한다. Rust 변경에는 사용 가능한 환경의 `cargo check`와 자료 접근 검증을 추가한다. Canvas·인코더를 모의한 테스트에 더해, 시간·미디어 구성 변경은 실제 브라우저에서 만든 MP4의 길이와 대표 경계를 확인한다.

작업 효율은 같은 제작안에서 기준 이미지 준비, 자막 수정, 장면 조정에 필요한 조작 수와 소요 시간을 적용 전후에 기록한다. 개선 폭은 이 비교 후 판단한다. 1080p 출력, 여러 화자, 여러 회차의 인물 라이브러리는 초기 범위의 검증 후 별도 확장으로 다룬다.

**C의 편집 검증과 형식 호환을 구현했다.** 원본 APP_DATA의 장면 번호·순서 검사는 유지하고, 편집 상태에서는 장면·자막 ID, 원본 연결, 현재 핵심 업적 연결, 자막 내용·시간과 장면 길이를 검사한다. `editor_version: 1`은 원본의 `schema_version`과 별개다. 기존 v1·2.0·2.1의 장면 ID·절대 시간·자료 경로를 바꾸지 않으며, 알 수 없는 JSON 필드도 저장·재열기·ZIP에서 보존한다. ZIP에는 v2 원본 `01_source/app_data.json`을 따로 포함한다.

로컬 웹은 IndexedDB 버전 6과 첫 저장 전 사본, 클라우드는 별도 저장 RPC와 버전 강등 차단·원본 보존 트리거·계정별 첫 변환 사본을 사용한다. 구형 클라우드 RPC는 새 형식 필드를 그대로 돌려보내더라도 새 형식의 저장을 거부한다. 운영 배포 전 [편집 호환성 SQL](../../supabase/migrations/202610200001_editor_compatibility.sql)을 먼저 적용해야 한다. SQL 누락 시 구형 함수로 우회하지 않는다. Tauri는 JSON 필드를 그대로 전달하고 업데이트한 네이티브 저장 경로에 버전 검사와 사본 보관을 추가했다. 이 환경에는 Cargo가 없어 Rust 컴파일과 패키징 앱 검증은 남아 있다. 기존 바이너리의 직접 파일 쓰기는 차단하지 못한다.

호환성 테스트는 v1·2.0·2.1 변환, 중복 ID·잘못된 시간·핵심 업적 연결, JSONB의 키 순서 차이, 늦게 도착한 자막 변경, 로컬·클라우드 저장과 ZIP을 다룬다. PGlite의 실제 PostgreSQL 엔진에서 새 SQL의 반복 설치, 첫 변환 사본, 구형 RPC·직접 쓰기의 버전 강등 차단, 원본 교체 거부와 계정별 사본 접근을 확인했다. 실제 Chromium의 로컬 모드에서는 저장소 버전 5의 프로젝트를 열고 자막 편집·실행 취소·다시 실행·새로고침·ZIP 내보내기를 수행했다. 원본·사본·자막 ID와 기존 시간 틈을 유지했고, 미래 형식 저장과 구버전 로컬 읽기를 차단했으며 페이지 오류는 0개였다. 실제 운영 Supabase/R2에 새 SQL을 적용한 검증은 별도다.

**D의 공통 시간 계산과 내레이션 길이 연동을 구현했다.** `timeline.ts`는 정수 밀리초로 장면 길이·장면 내 자막 위치를 계산하고 전체 누적 시각에서 15fps 경계를 정한다. 미리보기와 MP4의 장면·자막·음성·음악이 같은 프레임 계획을 사용한다. 기존 프로젝트를 열 때 시간을 바꾸지 않으며, 녹음 길이 조정을 적용할 때 대상 장면의 길이와 뒤 장면·자막 시간을 함께 갱신한다. 기존 시간 틈과 원본 제작안은 유지한다.

긴 녹음은 검사 후 저장 전에 조정안을 보여 준다. 기존의 짧은 녹음도 길이에 맞출 수 있으며, 자막 시간 유지와 비율 재배치, 장면별·자막별 변경 전후를 비교한다. 최소 자막 길이·겹침·장면 범위·전체 15분 제한을 검사한다. 녹음 끝이 잘리지 않도록 0.1초 단위 길이와 실제 프레임 수를 함께 검사한다. 조정 전체는 실행 취소 한 묶음이며, 업로드한 녹음은 유지한다. 시간을 되돌린 뒤 녹음이 장면보다 길어지면 출력 전에 다시 맞추도록 안내한다. 적용 중 다른 시간 편집이 들어오면 조정안을 다시 확인하게 하며, 이미지 생성처럼 시간과 무관한 늦은 결과는 새 편집과 함께 보존한다.

녹음은 새 ID의 파일로 준비하고 확인 후 연결하므로 조정안 취소·충돌·다른 프로젝트 이동이 기존 파일을 덮어쓰지 않는다. 시간 조정 또는 새 녹음을 처음 적용한 프로젝트만 편집 형식 2로 올린다. 운영 배포 전 [시간 편집 SQL](../../supabase/migrations/202610200002_timeline_editing.sql)을 추가로 적용해야 한다. 별도 RPC와 기존 버전 강등 차단을 사용하며, 첫 전환 전 편집 정보 사본을 로컬·계정·데스크톱에 보관한다. ZIP에는 ID가 붙은 녹음 파일과 표준 이름 사본을 함께 포함한다. Tauri 호출은 새 파일 ID와 기존 파일 읽기를 지원하도록 수정했으나 Cargo가 없어 네이티브 컴파일은 미검증이다.

검증은 39개 파일의 202개 테스트와 운영 빌드를 통과했다. 실제 Chromium에서는 1.1초 장면에 2.23초 WAV를 적용해 2.3초로 늘리고, 자막 비율 재배치·실행 취소·다시 실행·재열기·ZIP을 확인했다. 네이티브 AAC가 없는 이 Chromium에서는 [공식 AAC 확장](https://mediabunny.dev/guide/extensions/aac-encoder)을 필요할 때만 불러오는 경로로 음성 MP4를 완성했다. 실제 결과는 173프레임·11.533333초였으며 예상 프레임 수와 일치했다. AAC 트랙은 11.563537초로 영상과 약 0.030204초 차이였고 한 프레임 이내였다. 장면 경계 전후의 이미지, 두 자막의 화면, 녹음 앞뒤 무음과 끝부분의 음성을 디코딩해 확인했다. 페이지 오류는 0개였다. 클라우드 쓰기·충돌·새 SQL은 모의 저장과 PGlite 범위이며, 실제 운영 계정의 새 SQL 적용·R2·패키징 앱 검증은 별도다.

**E의 자료 목록과 구간 구성을 구현했다.** `media.assets`는 모든 이미지·동영상·녹음·음악에 프로젝트 범위 ID와 원본 경로·계정 키·기존 IndexedDB 위치를 부여한다. 장면의 `composition`은 순서가 있는 화면 구간과 원본 시작·종료·장면 내 배치를 가진 음성 구간을 보관한다. 기존 화면 선택·앞 이미지·트림·보조 이미지·단일 녹음을 어댑터로 변환하며, 미리보기와 MP4가 같은 구성에서 재생 계획을 만든다. 표시 번호 변경은 파일 위치나 자료 ID를 바꾸지 않는다. 데스크톱의 동영상·녹음 읽기도 원본 경로를 전달하도록 수정했다.

원본은 프로젝트를 삭제할 때까지 보관한다. 후보·녹음·음악의 연결 해제와 교체는 원본을 제거하지 않고, 클라우드의 개별 파일 삭제 API도 자료 목록에 보관된 원본·포스터를 거부한다. 새 녹음과 음악은 ID가 붙은 `01_source/media/` 파일을 사용한다. 계정 이전은 편집에서 빠진 원본까지 복사하며, ZIP은 모든 원본과 자료 ID별 경로 목록을 포함하고 현재 표시 번호의 폴더에 선택 파일을 배치한다. 원본 제작안·알 수 없는 메타데이터·기존 파일 경로는 유지한다.

자료가 있는 프로젝트를 저장하면 편집 형식 3으로 전환하고 첫 저장 전 JSON 사본을 보관한다. 별도의 RPC와 원본 자료의 위치 교체·삭제 방지 트리거를 사용하므로 운영 배포 전 [자료 구성 SQL](../../supabase/migrations/202610200003_media_composition.sql)을 추가로 실행해야 한다. 형식 1·2 저장 계약과 구버전 차단을 유지한다. 자료가 없는 프로젝트는 기존 저장 함수를 사용한다.

검증은 41개 파일의 215개 테스트와 운영 빌드를 통과했다. PGlite에서 SQL 반복 적용, 첫 전환 사본, 구형 RPC·직접 쓰기의 원본 삭제·경로 교체 차단, 충돌, 계정별 사본 접근과 프로젝트 삭제 시 정리를 확인했다. 실제 Chromium에서는 번호가 1에서 3으로 바뀐 장면에 두 화면 구간을 넣고 앞 이미지→원본 동영상의 0.4~1.4초 구간→보조 이미지→별도 이미지를 미리보기와 MP4에서 비교했다. 녹음 원본의 0.2~0.7초와 1.2~1.7초를 서로 다른 위치에 배치해 두 음성과 중간 무음을 디코딩했다. MP4는 195프레임·13초로 계획과 일치했고 AAC 차이는 약 0.0264초였다. ZIP에는 원본 8개와 두 화면·두 음성 구간이 남았으며 페이지 오류는 0개였다. 기존 D의 시간 조정·취소·실행 취소·재열기·MP4·ZIP도 실제 브라우저에서 다시 통과했다. 운영 Supabase/R2의 쓰기와 패키징한 Tauri 앱은 별도 검증 대상이며, 이 환경에는 Cargo가 없어 네이티브 컴파일을 확인하지 못했다.

**F1의 장면 순서 변경을 구현했다.** Scene 검토의 순서 앞으로·뒤로 버튼은 최신 프로젝트에서 현재 장면 ID를 찾아 인접 장면과 맞바꾼다. 표시 번호와 장면·자막의 절대 시간을 정수 밀리초로 재계산하며 장면 길이·자막의 장면 내 위치·자료 구성·녹음·핵심 업적 ID·원본 출처와 제작안은 보존한다. 시간 틈이 있던 프로젝트는 이동 시 연속 본문 시간으로 정리하며 실행 취소에서 이전 번호·순서·시간 틈을 복원한다. 선택한 편집 장면은 이동 후에도 유지한다.

배열 순서를 유지하던 저장 병합에는 명시적인 순서 변경만 반영하는 경로를 추가했다. 이동 전 시작한 생성·업로드는 장면 ID로 최신 상태에 병합하고, 늦게 도착한 자막 시간 변경은 현재 장면의 시작 시각으로 옮겨 비교한다. 실행 취소는 전체 장면 스냅샷을 복구하지 않고 순서·번호·시간 필드만 되돌려 새 자료와 다른 편집을 보존한다. 순서 변경 이력은 별도 한 묶음이며 앞서 편집한 자막 이력도 유지한다. 저장 실패 시 새 순서와 이력을 유지해 재시도한다. 기존 편집 형식·저장 RPC를 사용하므로 추가 SQL은 없다.

검증은 43개 파일의 231개 테스트를 통과했다. v1·2.0·2.1, 시간 틈·소수 초·핵심 업적 연결, 이동·실행 취소·다시 실행, 생성·녹음의 늦은 완료, 저장 실패·재시도, 계정 저장의 연속 리비전과 로컬 저장·재열기·ZIP을 확인했다. 실제 Chromium에서는 두 화면·두 음성 구간이 있는 장면을 UI에서 1번→3번으로 옮기고 두 번의 실행 취소·다시 실행·재열기를 수행했다. 선택 장면과 미리보기 1.2초 위치가 유지됐고, 전체 검토와 실제 완료 화면의 MP4 생성이 새 순서와 일치했다. 결과는 195프레임·13초, AAC 차이 약 0.0264초였으며, 이미지·동영상·보조 화면·부분 녹음과 중간 무음을 디코딩해 확인했다. ZIP은 원본 8개, 새 번호의 선택 파일, 두 화면·두 음성 구간과 원본 제작안을 보존했다. 페이지 오류는 0개였다. 운영 Supabase/R2의 실제 쓰기와 패키징한 데스크톱 앱은 별도 검증 범위다.

**F2의 자막 경계 나누기를 구현했다.** APP_DATA 2.1의 다음 자막 시작을 선택해 앞·뒤 길이를 확인하고 각각 1초 이상인 두 장면으로 나눈다. 앞 장면의 ID와 활성 선택을 유지하고 뒤 장면에 독립 ID를 부여하며 표시 번호를 다시 매긴다. 자막 ID·문구·절대 시간·시간 틈, 전체 길이, 원본 제작안과 원본 장면 연결을 보존한다. 핵심 업적 장면을 나누면 양쪽 장면이 그 연결을 이어받는다.

분할 구간은 원본 화면의 재생 시계와 동작 효과 진행률을 보관한다. 앞 이미지→동영상, 원본 트림, 마지막 화면 유지, 보조 이미지의 페이드와 강조 자막이 분할점에서 다시 시작하지 않는다. 분할점이 앞 이미지 안에 있어 한쪽 장면에 동영상 프레임이 없는 경우도 실제 Chromium MP4 비교를 통과했다. 음성은 원본 소스 구간을 나누고 프레임 경계의 오차를 별도 배치 오프셋으로 보정한다. 연속한 원본 녹음은 전체 미리보기와 MP4에서 한 구간으로 읽어 중간 페이드나 무음을 만들지 않으며, 분할 이후에만 시작하는 녹음도 원래 시간을 유지한다. 장면별 미리듣기·파형과 ZIP의 `narration.wav`는 해당 구간과 무음을 포함한 WAV로 준비하고 스테레오 채널을 유지한다. 온전한 원본 파일은 자료 목록과 ZIP에 그대로 남긴다.

실행 취소는 장면 추가·공통 장면 필드·핵심 업적 연결을 한 묶음으로 복원한다. 중첩 분할을 모두 취소한 동안에도 복원할 자식 장면의 이력을 보관한다. 뒤늦게 완료된 생성·업로드는 최신 장면 ID로 병합하고, 취소로 빠진 자식의 결과는 원본 목록에 보관하면서 다시 실행할 장면에도 반영한다. 새 녹음의 시간 조정에서는 화면 구간 이력과 녹음 연결을 따로 다뤄 취소·다시 실행으로 파일을 잃거나 길이를 잘못 복원하지 않는다. 분할 장면의 기존 전환·트림 조절은 구간 요약으로 표시하며 다른 화면 선택·이미지 효과·보조 이미지 선택·녹음 교체는 해당 장면에 적용한다.

분할한 프로젝트는 **편집 형식 4**와 `great100_save_structured_project`를 사용한다. 실행 취소 후에도 버전을 내리지 않으며 구형 저장 함수로 우회하지 않는다. 배포 전 [장면 나누기 SQL](../../supabase/migrations/202610200004_scene_splitting.sql)을 E의 SQL 뒤에 실행해야 한다. 첫 전환 전 사본은 계정의 `great100_structure_backups`, 로컬의 `editor-backup:<프로젝트 ID>:3`(직전 버전이 3인 경우), 데스크톱의 `project_data.pre-editor-v4.json`에 보관한다. 계정 이전도 형식 4와 분할 구간을 보존한다. 미리보기·음성 계산 변경에 맞춰 MP4 캐시 버전은 11로 올렸다.

검증은 **45개 파일의 257개 테스트와 운영 빌드**를 통과했다. 경계·최소 길이·겹치는 자막, 중첩 분할, 원본 구간·핵심 업적 연결, 긴 녹음 조정, 생성의 늦은 완료, 로컬 저장·재열기·사본·삭제, 계정 이전과 버전 4 RPC를 확인했다. PGlite에서 SQL 반복 적용·전환 사본 1회 보관·구형 RPC 차단·낙관적 충돌·원문과 원본 파일 불변·타 계정 격리와 사본 정리를 확인했다.

실제 Chromium에서는 4초 장면을 1.1초와 2.3초 자막 경계에서 중첩 분할하고 두 번의 취소·복원·재열기를 수행하고 개별 장면의 녹음 구간을 디코딩했다. 전체 검토와 완료 화면에서 만든 MP4는 **195프레임·13초**, AAC와 차이는 약 **0.0264초**였다. 분할 전후 디코딩한 화면 픽셀과 분할점 양쪽의 음성을 비교해 동영상·정지 화면·보조 이미지와 연속 음성의 일치를 확인했다. ZIP에는 원본 8개와 각 분할 장면의 WAV가 남았고 원본 녹음의 SHA-256과 원본 제작안이 일치했다. 페이지 오류는 0개였다. 기존 F1의 순서 변경·부분 음성 출력과 D의 긴 녹음 시간 조정·취소·저장·MP4·ZIP도 실제 브라우저에서 회귀 검증을 통과했다. 운영 Supabase/R2의 실제 쓰기와 패키징한 Tauri 앱은 검증하지 않았으며, 이 환경에 Cargo가 없어 네이티브 컴파일은 확인하지 못했다.

**F3의 인접 장면 합치기를 구현했다.** APP_DATA 2.1의 현재 장면에 다음 장면을 이어 붙인다. 대상 장면·합친 길이를 먼저 표시하며 두 화면을 선택하고 합계 120초 이하일 때 적용한다. 첫 장면의 고정 ID와 활성 선택을 유지하고 번호를 다시 매긴다. 자막 ID·문구·상대 시간, 두 장면의 원본 출처·이미지 후보·동영상·보조 이미지·녹음을 보존하고, 핵심 업적 연결을 첫 장면 ID로 옮긴다. 원문과 원본 JSON은 그대로 유지한다. 내부의 절대 시간 틈은 장면 길이의 합으로 정리하고 나머지 장면의 절대 시간은 유지한다.

F2의 원본 재생 시계 캡처를 공통 함수로 분리했다. 합치기 전에 각 화면의 동영상 트림·앞 이미지·보조 화면·정지 화면·효과 진행률을 보관하고 강조 문구·노출 나이·음악 볼륨도 구간마다 보관한다. 합친 뒤 밀리는 다른 장면의 자동 움직임도 기존 효과를 유지한다. 녹음에는 원래 장면의 프레임 종료 경계를 보관해 첫 장면의 반올림 잔여 시간이 두 번째 녹음에 섞이지 않도록 한다. 분할한 동일 녹음의 연속성은 계속 유지한다. 개별 장면 미리보기의 두 번째 화면 구간에 전체 영상 오프닝용 자막 페이드를 적용하던 조건도 바로잡았다.

합치기는 장면 제거·공통 필드·원본 출처·핵심 업적·후보 목록을 한 번에 되돌린다. 후보 목록은 ID에 따른 변경만 복원하므로 뒤늦게 도착한 업로드를 잃지 않는다. 제거될 두 번째 장면에 있던 이전 편집 이력도 유지하고, 진행 중이던 생성 결과는 합친 후보 목록과 보관 원본에 추가하며 취소에서 복원할 원래 장면에도 반영한다. 연속 합치기, 두 번의 취소·복원, 합친 뒤 재분할을 지원한다. 재분할한 뒤 장면의 기본 강조 문구·볼륨은 첫 보존 구간에 맞춘다. 강조·음악 설정 변경은 현재 장면 전체에 적용하고, 화면 교체는 현재 장면의 설정으로 전체 화면 구성을 교체한다.

구간별 표현과 녹음의 원래 재생 한계를 구버전 앱이 무시하지 못하도록 **편집 형식 5**와 `great100_save_merged_project`를 추가했다. 운영 배포 전에 [장면 합치기 SQL](../../supabase/migrations/202610200005_scene_merging.sql)을 F2 SQL 뒤에 적용해야 한다. 첫 전환 전 JSON은 계정의 `great100_merge_backups`, 로컬의 `editor-backup:<프로젝트 ID>:<직전 버전>`, 데스크톱의 `project_data.pre-editor-v5.json`에 한 번 보관한다. 형식 1~4의 기존 저장 계약은 유지하고 형식 5 요청은 이전 함수로 우회하지 않는다. 계정 이전에서도 구간별 강조·음악과 녹음 경계를 보존한다.

검증은 **46개 파일의 277개 테스트와 운영 빌드**를 통과했다. 합치기 전후 원본·핵심 업적·후보·효과·음성 시간, 내부 시간 틈, 소수 초, 합계 길이 제한, 합치기와 재분할, 이전 이력, 생성의 늦은 완료, 로컬 사본·재열기·삭제와 계정 이전을 검증했다. PGlite에서는 SQL 반복 적용, 첫 전환 사본, 원문·원본 자료 불변, 구형·타 계정 쓰기 차단, 충돌과 사본 정리를 확인했다.

실제 Chromium에서는 이미지·트림 동영상·보조 이미지와 서로 다른 WAV 녹음 두 개가 있는 세 장면을 3→2→1개로 합쳤다. 두 번의 취소·다시 실행, 재분할과 취소·복원, 저장·재열기, 개별·전체 미리보기와 실제 완료 화면의 MP4 생성을 수행했다. MP4는 **195프레임·13초**, AAC와 차이는 약 **0.0264초**였다. 합치기 전후 화면과 강조 문구·자막, 두 녹음을 디코딩해 비교하고 음악 볼륨 10%→85%→30%를 확인했다. 실제 렌더러의 인코딩 전 47·63·82·113번 프레임도 비교해 픽셀 차이가 0임을 확인했다. ZIP은 원본 10개, 세 화면·두 음성 구간과 합친 WAV를 보관했고 두 녹음 원본의 SHA-256과 원본 제작안이 일치했다. 페이지 오류는 0개였다. F2의 앞 이미지 내부 분할·중첩 나누기·취소·복원·재열기·MP4·ZIP도 실제 Chromium에서 회귀 검증했다. 운영 Supabase/R2의 실제 쓰기와 패키징한 Tauri 앱은 별도 검증 범위이며, 이 환경에는 Cargo가 없어 네이티브 컴파일을 확인하지 못했다.

**F의 순서 변경·나누기·합치기가 연결됐다.** G1은 다음과 같이 단일 장면의 내레이션 생성·검토·적용을 연결했고 현재는 기본 숨김이다. H1의 전체 장면 작업 보드는 아래 구현 결과를 참고한다. API 도입을 요구하는 품질 평가·발화 정렬·생성 큐는 후속 선택 범위이며 현재는 API 없는 제작 편의를 우선한다.

**G1의 장면별 AI 내레이션 생성 경로를 구현했다.** OpenAI [종료 일정](https://developers.openai.com/api/docs/deprecations)에서 기존 `tts-1`·`tts-1-hd`와 GPT-4o mini TTS 스냅샷이 2027년 1월 6일 종료 예정임을 확인했다. 새 구현은 기존 서버 키를 사용할 수 있는 `gpt-audio-1.5`의 [Chat Completions 오디오 생성](https://developers.openai.com/api/docs/guides/audio-chat-completions)을 선택했다. 전용 TTS처럼 응답 문구가 고정된 계약은 아니므로 전체 낭독 지시와 응답 transcript의 단어 일치 검사를 추가하고, 잘린 응답·문구 추가·누락은 거부한다. 띄어쓰기·구두점·대소문자 차이는 허용하며 숫자의 읽기 표기가 달라도 현재는 재생성을 요구한다. 7개 기본 목소리와 느리게·보통·빠르게의 지시형 속도를 제공한다. 정밀 배속, 단어 타임스탬프와 강제 정렬은 이번 범위에 포함하지 않는다.

공급자 [모델 문서](https://developers.openai.com/api/docs/models/gpt-audio-1.5)의 가격은 100만 토큰 기준 텍스트 입력 $2.50·출력 $10, 오디오 입력 $32·출력 $64다. 길이·토큰 종류에 따라 비용이 달라지므로 정액 예상 비용을 UI에 표시하지 않는다. 생성과 재생성은 별도 요청 ID로 추적하고 자동 재시도하지 않는다. 서버는 Supabase 로그인 세션을 검증한 뒤 고정 모델·허용 목소리·속도·1800자 제한을 확인한다. 서버에만 보관한 `OPENAI_API_KEY`를 사용하고 대시보드의 키 입력란은 계속 숨긴다. 출력은 최대 400만 자의 base64 MP3이며 브라우저에서 실제 디코딩 길이·120초 제한을 확인한다. 서버에는 원문·음성·인증값을 제외한 호출 ID·계정 ID·공급자 상태·제공된 토큰 사용량만 기록한다. 시간 초과·대기 중단 후 재요청은 추가 사용량이 발생할 수 있음을 표시한다.

APP_DATA 2.1은 현재 편집한 captions 문구를 읽고 다른 형식은 편집한 narration을 사용한다. 생성한 파일은 먼저 메모리에서 미리듣고 적용할 때 기존 원본 보관 경로로 저장한다. 생성 이후 대본·음성 선택·구조·옵션 변경을 감지하고, 저장 중 발생한 대본·시간·녹음 변경은 루트의 최신 프로젝트와 다시 비교한다. 저장한 미적용 파일은 유효한 재시도에서 재사용하며 취소하면 정리한다. 적용한 음성과 전체 시간·자막 변경은 한 번에 취소·복원하고, 합친 장면의 기존 여러 녹음 구간도 복구한다. 원본 자료 목록과 늦은 이미지 결과는 유지한다. 첫 자료 변환에서 생기는 asset ID·구간 구성도 양쪽 이력에 정규화해 취소 이후 다시 실행이 충돌하지 않도록 했다.

생성 메타데이터는 선택 음성과 원본 자료에 보관하고 장면 나누기·합치기 이후에도 원본에서 확인할 수 있다. 직접 적용한 AI 음성의 자막이 바뀌면 불일치를 표시한다. ZIP에는 원래 MP3와 기존 녹음, 생성 요청·대본·목소리·속도·사용량 로그를 포함한다. 저장된 음성 자체가 기존 자료 구조와 동일하므로 새 편집 버전·SQL·네이티브 명령을 추가하지 않았다. 생성은 로그인한 웹에서 제공하며 데스크톱의 녹음·업로드와 기존 음성 출력은 유지한다.

검증은 **49개 파일의 303개 테스트와 운영 빌드**를 통과했다. 인증·서버 설정·잘못된 옵션·길이·공급자 오류·문구 불일치·잘린 응답·자동 재시도 없음, 생성 중 대본 변경·저장 중 시간 변경·옵션 변경·대기 중단, 불일치 표시, 저장 실패·파일 재사용, 합친 녹음 복원과 원본 메타데이터 보존을 확인했다. 실제 Chromium에서는 인증과 공급자 응답만 모의하고 실제 MP3를 디코딩·미리듣기·적용했다. 2초 장면에 3.264초 음성을 적용해 3.3초 장면과 이후 자막 시간을 갱신하고 취소·다시 실행·대본 변경·불일치·재열기·전체 미리보기와 완료 화면의 MP4를 확인했다. 결과는 **215프레임·14.333초**, AAC 차이는 약 **0.0398초**였고 실제 음성 구간을 디코딩했다. ZIP의 생성 MP3 SHA-256이 원본과 일치했고 보관 파일 7개·기존 녹음·원문과 요청 로그를 유지했다. 페이지 오류와 중복 요청은 없었다.

이 환경에는 OpenAI API 키와 운영 로그인 세션이 없어 유료 공급자 호출, 실제 한국어 발음·고유명사·숫자 품질, 비용·지연·계정별 모델 접근, 운영 Supabase/R2 쓰기는 검증하지 못했다. 이는 생성·저장 경로의 모의 검증과 구분한다. G1 API 경로를 나중에 활성화한다면 서버 키와 `VITE_ENABLE_AI_NARRATION=true`를 설정하고 짧은 한국어 표본으로 이 항목들을 확인해야 한다. 현재 Plus만 사용하는 환경에서는 필요하지 않다. 실제 발화 시점 자막 정렬과 여러 장면의 일괄 생성·취소·부분 재시도는 G2/H의 후속 범위다.

**H1의 전체 장면 작업 보드를 구현했다.** 기존 전체 검토의 이미지 목록을 화면·보조 자료·자막·녹음·길이·핵심 업적 상태 카드로 확장했다. 화면 미선택·녹음 없음·시간 오류를 각각 집계하고 필터링하며, 녹음은 선택 사항으로 표시해 완료 조건과 구분한다. 선택 후보 ID만 보는 대신 공통 자료 구성과 원본 목록을 읽어 나눈 장면·합친 장면의 여러 화면과 녹음도 표시한다. 상태 판정은 읽기 전용이며 원본 파일·데이터를 변경하지 않고 생성 API를 호출하지 않는다. 실제 원본 파일의 존재나 서명 URL 유효성을 보증하는 검사는 아니며 기존 전체 미리보기와 출력 경로에서 확인한다. 기존 전체 영상 미리보기·썸네일·완료 전 검사도 유지한다.

카드에서 해당 고정 ID의 장면 편집으로 이동하고 보드로 바로 돌아올 수 있다. 필터·스크롤과 원래 카드의 화면 내 위치를 프로젝트별 메모리에 보관하므로 장면을 옮겨도 같은 카드를 찾아 초점을 복원한다. 수정으로 필터에서 빠지거나 편집 중 다른 장면에 합쳐졌으면 기존 필터와 가능한 스크롤을 유지하고 필터 버튼에 초점을 둔다. 이 상태는 앱을 열어 둔 동안 유지하고 새로고침 시 초기화한다. 편집 장면 선택도 상위 상태에서 ID로 보관한다. 브라우저 이력에는 현재 장면 ID를 함께 보관하되 같은 화면의 장면 탭 이동은 현재 이력만 갱신하고 추가 이력을 쌓지 않는다. 첫 진입 때 선택 ID를 확정해 순서 변경으로 다른 장면이 선택되던 회귀도 방지했다.

장면 길이·시작/종료 불일치·장면/자막 겹침·자막 범위·동영상 원본 트림·보조 화면 전환·녹음 원본 구간과 재생 한계를 시간 오류로 안내한다. 원본 연결 문제와 미리보기 로드 실패는 별도로 안내한다. 보드 필터와 탐색 상태는 프로젝트 JSON·편집 형식·저장 RPC를 변경하지 않으므로 추가 SQL과 API 키가 필요 없다.

검증은 **51개 파일의 317개 테스트와 운영 빌드**를 통과했다. v1·2.0·2.1의 읽기 전용 집계, 분할·합친 원본과 보조 화면·녹음, 자막 오류·잘못된 원본 구간·유효하지 않은 길이, 필터·원본 보존, 정확한 장면 이동, 필터 해소·스크롤/초점 복원·다른 프로젝트 격리·합쳐져 사라진 장면·브라우저 뒤로/앞으로를 확인했다. 기존 순서 변경·나누기·합치기·비동기 저장/편집 이력도 회귀 검증했다.

실제 Chromium에서는 18개 원본 장면 중 두 장면을 합친 **17개 장면**의 대표 제작안을 사용했다. 미선택 화면 3개·녹음 없는 장면 16개를 집계하고, 후보 선택으로 필터에서 빠지는 장면과 자막 오류를 수정해 빈 결과로 돌아오는 흐름을 확인했다. 장면 16을 앞으로 옮겨도 같은 ID를 편집했고, 보드 복귀 시 카드 상단 위치는 **344.890625px → 344.890625px**로 유지됐다(기존 스크롤 1610px). 키보드 초점, 브라우저 뒤로/앞으로, 실제 전체 미리보기와 원문 보존을 확인했다. 생성 API 호출·페이지 오류는 0개였다. 기존 데스크톱 최소 너비 정책을 유지하며 패키징한 Tauri 앱과 운영 계정의 실제 저장은 별도 검증 범위다.

**H2의 장면 이미지 일괄 업로드·배치를 구현했다.** 전체 검토에서 PNG·JPEG·WebP를 각 12MB, 최대 40장·합계 120MB까지 준비한다. 명시적인 `scene_01`·`장면2` 또는 파일명 앞의 `03_` 번호로 현재 장면의 연결안을 제안하며, 날짜·번호 없는 이름·서로 다른 장면 번호가 있는 이름은 추측하지 않는다. 파일 내용·MIME·크기와 실제 이미지 디코딩을 확인한 뒤 파일별 미리보기·연결 장면·현재 화면·적용 방식을 표시한다. 사용자가 적용하기 전에는 업로드하거나 프로젝트를 저장하지 않으며 미연결 파일과 손상 이미지는 제외한다.

기본값은 기존 화면을 유지하고 빈 장면만 채우는 방식이다. 교체를 선택하면 해당 장면 전체 화면을 새 이미지로 바꾼다. 같은 장면의 첫 유효 파일만 대표 화면에 적용하고 나머지는 후보로 보관하며, 중단·재개와 부분 실패 재시도에서도 이 우선순위를 유지한다. 장면 연결은 고정 ID를 사용하고 업로드 전 검토한 화면 구성을 적용 직전에 다시 비교한다. 순서 변경은 같은 장면에 연결하고 화면 변경은 후보로만 추가하며, 합치기·나누기·취소로 장면이 없어진 경우 원본 자료 목록에 보관한다. 화면 선택은 편집 이력으로 되돌리고 후보와 기존 원본은 보존한다.

파일을 순차 처리하고 성공·실패·대기를 각각 유지하며 실패 파일만 재시도하거나 현재 파일 완료 후 중단할 수 있다. 프로젝트 저장 실패는 기존 저장 재시도로 처리해 성공한 파일을 중복 업로드하지 않는다. 목록·파일·연결안은 Studio 루트에서 프로젝트별로 관리해 장면 이동·프로젝트 전환 중에도 유지하며, 새로고침·앱 종료 시 초기화한다. 목록 제거와 종료 시 임시 미리보기 URL을 해제한다. 업로드 중에는 프로젝트 삭제·로그아웃을 막고 페이지 이탈 안내를 유지한다. 기존 원본 저장·편집 형식·RPC를 재사용하므로 새 SQL·네이티브 명령·API 키가 필요하지 않으며 API 음성 생성과 키 입력은 계속 기본 숨김이다.

검증은 **53개 파일의 334개 테스트와 운영 빌드**를 통과했다. 번호 추론·안전한 미연결, 고정 ID와 순서 변경, 선택한 동영상·자동 앞 이미지·합친 구간 유지, 교체 취소·원본 보존, 업로드 중 직접 선택, 부분 성공·실패만 재시도·중단 재개, 프로젝트 격리·URL 정리, 크기·형식·손상 이미지와 프로젝트 저장 실패를 확인했다.

실제 Chromium에서는 8개 원본 장면을 7개로 합친 제작안에 세 이미지 형식과 손상·미연결 파일을 함께 넣었다. 장면 이동 후 연결 유지, 첫 4개 성공과 파일 읽기 실패 1개의 단독 재시도, 같은 장면의 복수 후보, 합친 화면 유지·교체 취소·복원, 실제 IndexedDB 쓰기 실패와 파일 재업로드 없는 저장 복구·재열기·전체 미리보기를 확인했다. ZIP의 기존 원본 **10개 SHA-256이 전부 일치**했고 새 성공 파일 8개를 포함한 원본 18개와 원문 JSON을 보존했다. 생성 API 호출과 페이지 오류는 0개였다. 이번 변경은 렌더러를 수정하지 않았으며 운영 Supabase/R2의 실제 쓰기와 패키징한 Tauri 앱은 별도 검증 범위다.


**H3의 후보 이미지 비교·최종 선택을 구현했다.** 전체 검토의 장면 카드에서 기본 dialog 비교 창을 열어 메인 이미지 후보를 최대 4장씩 크게 비교한다. 현재 단일 이미지와 합친 장면의 각 이미지 구간을 먼저 포함하고, 후보 목록에서 비교할 이미지를 바꾼다. 현재 선택·사용 구간과 임시 검토 선택을 구분하며 확인한 이미지만 명시적인 선택 확정으로 반영한다. 이미지 로딩 실패는 선택을 막고 해당 미리보기만 다시 불러올 수 있다. 동영상은 현재 화면 구간의 대표 이미지만 표시하고 이미지 후보 선택에서는 제외한다.

열 때의 보드 필터에 포함된 고정 장면 ID를 보관해 선택 후 필터에서 빠져도 연속 검토가 가능하다. 장면 순서는 현재 번호 순으로 표시하며 이전·다음 또는 선택 확정 후 다음 장면으로 이동한다. 이동·닫기는 미확정 선택을 초기화하고, 닫을 때 마지막 검토 카드의 위치·초점을 복원한다. 카드가 필터에서 빠지거나 없어졌으면 필터와 가능한 스크롤을 유지하며 필터 버튼에 초점을 둔다. 기본 dialog의 모달·Esc 동작을 사용하고 창을 연 동안 배경 스크롤을 잠근다. 비교 상태는 프로젝트 데이터에 저장하지 않는다.

확정 직전에 최신 프로젝트·장면·이미지 후보 ID와 검토한 화면 구성을 다시 확인한다. H2와 공통 화면 비교 기준을 사용해 번호·무관한 자막 변경과 실제 화면 변경을 구분한다. 확정은 장면 전체의 주 화면을 바꾸며 합친 첫 이미지의 기존 선택 ID가 같아도 여러 구간을 한 이미지로 교체할 수 있다. 기존 구간별 녹음·자막·길이·원문·핵심 업적·후보·원본을 보존하고 화면 선택 및 구간 구성만 편집 이력으로 취소·복원한다. 저장 중 중복 확정·장면 이동을 막고 창을 닫은 뒤 완료된 요청은 장면 이동을 일으키지 않는다. 저장 중 다른 편집이 반영되면 현재 화면을 다시 확인하도록 안내한다. 저장 실패는 창 안에서 안내하고 자동으로 다음 장면으로 가지 않으며 기존 저장 재시도를 사용한다. 편집 형식·저장 RPC·네이티브 명령·SQL은 변경하지 않았고 API 키 입력과 API 음성 생성 UI는 계속 기본 숨김이다.

검증은 **55개 파일의 354개 테스트와 운영 빌드**를 통과했다. 형식 1·2.0·2.1, 비교 목록·동영상 제외, 읽기 전용 임시 선택, 고정 장면 ID·후보 소실·오래된 선택, 합친 첫 이미지 교체와 나눈 음성 구간 보존, 늦은 후보 추가 후 취소·복원, 필터에서 빠진 장면의 연속 검토, 이미지 로딩 재시도·Esc·초점 복원, 저장 실패·저장 중 닫기·실행 취소를 확인했다. 기존 작업 보드·일괄 업로드·편집 이력·클라우드 저장·SQL 계약도 회귀 테스트를 통과했다.

실제 Chromium에서는 8개 원본 장면을 합친 7개 장면과 이미지·실제 MP4·두 WAV 원본을 사용했다. 2장·4장 비교, 모달 초점·Esc와 확정 전 데이터 불변, 필터 유지·연속 확정, 합친 첫 이미지 전체 교체·취소·복원, 검토 중 실행 취소에 따른 재검토, 동영상 제외·교체 취소 시 앞 이미지·트림 복원, 실제 IndexedDB 저장 실패와 재시도·재열기·전체 미리보기를 확인했다. 카드 상단은 **200.140625px → 200.140625px**로 복원됐고, 1440px·1080px 너비의 비교 창을 확인했다. ZIP의 기존 **원본 53개 SHA-256이 전부 일치**했으며 녹음 구간·원본 제작안도 보존했다. 생성 API 호출과 페이지 오류는 0개였다. 렌더러 변경은 없으며 운영 Supabase/R2 실제 쓰기와 패키징한 Tauri 앱은 별도 검증 범위다.


**H4의 이미지 원본 보관함·후보 복원을 구현했다.** 전체 검토에 기본 접힘 패널을 추가해 자료 목록의 이미지 원본을 9개씩 표시한다. 파일명·장면 제목 검색, 화면 연결됨·연결 없음·후보 목록에서 빠짐 필터를 제공한다. 선택한 인물 기준 이미지·썸네일과 현재 장면 구성의 주 화면·앞 이미지·보조 화면 연결을 후보 보관 위치와 따로 표시한다. 나누거나 합친 장면도 실제 구성 참조를 읽으며, 일부 구성을 읽지 못하면 알 수 없는 연결을 미사용으로 판정하지 않는다. 표시된 연결은 편집 메타데이터 기준이며 실제 파일 가용성은 미리보기와 복원 시 확인한다. 닫힌 패널은 원본을 읽지 않고, 페이지에서 생성한 임시 미리보기 URL은 교체·종료 시 해제한다.

사용자가 장면을 명시적으로 선택하면 원본 바이트의 크기·형식·이미지 디코딩을 확인한 뒤 기존 자료 ID·경로·저장 키를 재사용해 메인 후보에 추가한다. PNG·JPEG·WebP와 기존 mock SVG를 지원하며 12MB를 넘거나 손상된 원본은 추가하지 않는다. 현재 화면은 빈 장면에서도 자동 선택하지 않고 선택한 동영상의 자동 앞 이미지도 기존 이미지 또는 없음으로 고정한다. 합친 화면·녹음·자막과 원문은 유지한다. 같은 장면에 이미 있는 후보는 중복 추가하지 않는다. 복원은 원본 재업로드나 파일 복사를 일으키지 않으며 다른 편집을 취소해도 후보와 원본은 보관한다. 저장 실패는 기존 저장 재시도로 처리한다.

복원 직후 필터에서 카드가 사라져도 상단 결과와 후보 비교 진입을 유지한다. H3 비교를 재사용하되 보관함 경로는 프로젝트의 모든 장면을 탐색하고, 닫으면 실행한 버튼과 스크롤을 복원한다. 복원 도중 장면 이동·순서 변경이 있어도 최신 프로젝트의 고정 장면 ID를 사용하며 장면이 합쳐져 사라지거나 원본 정보가 바뀌면 추가를 거부한다. 작업 중 새로고침·프로젝트 삭제·로그아웃과 페이지 이탈을 기존 저장 흐름과 함께 보호한다. 현재 앱의 `candidate:` 자료 ID가 없는 외부 이미지 메타데이터는 조회·ZIP 확인만 지원한다. 편집 버전·저장 RPC·SQL·네이티브 명령은 추가하지 않았고 API 키와 음성 생성 UI는 기본 숨김을 유지한다.

검증은 **58개 파일의 380개 테스트와 운영 빌드**를 통과했다. v1·2.0·2.1의 원본 식별 정보 유지, 기준 이미지·썸네일·보조 화면·합친 구간의 연결 집계, 손상 구성 판정, 중복 방지·빈 화면 유지·동영상 앞 이미지 고정, 편집 취소 후 후보 보관, 비동기 읽기 중 이동·장면 소실·원본 변경, 미리보기 재시도·URL 해제·필터·페이지·검색·비교 초점 복원을 확인했다. 로컬 저장·재열기·ZIP의 동일 바이트와 기존 R2 키를 사용하는 클라우드 저장의 업로드 없음도 검증했다.

실제 Chromium에서는 8개 원본 장면을 합친 7개 장면과 이미지 50개·MP4 1개·WAV 2개를 사용했다. 후보 목록에서 제거한 이미지를 보관함에서 찾아 빈 장면·동영상 장면·합친 장면에 복원하고, 기존 화면 유지·비교 확정·취소·다시 실행·초점 복귀를 확인했다. 원본 읽기 실패와 PNG 헤더만 있는 손상 바이트는 후보 추가 없이 재시도했고, 실제 IndexedDB 프로젝트 쓰기 실패는 원본을 다시 읽지 않고 저장 재시도로 복구했다. 원본 파일 저장소 쓰기는 0회였고 ZIP의 **원본 53개 SHA-256이 전부 일치**했다. 원문·합친 녹음 구간·동영상 앞 이미지·트림·재열기와 실제 전체 미리보기를 확인했으며 1440px·1080px에서 보관함이 너비에 맞았다. 생성 API 호출과 페이지 오류는 0개였다. 렌더러 변경은 없으며 운영 Supabase/R2 실제 쓰기와 패키징한 Tauri 앱은 별도 검증 범위다.


**H5의 MP4 출력 전 실제 자료 점검을 구현했다.** 전체 검토에서 사용자가 자료 점검을 실행하면 현재 출력에 연결된 원본과 대표 이미지를 순차 확인한다. 공통 영상 계획에 주 화면·보조 화면의 자료 ID를 추가해 출력과 같은 화면 구성·프레임 시간·오프닝·엔딩을 사용한다. 나누거나 합친 장면의 화면·녹음 구간도 포함하며, 후보에만 있는 자료와 출력에 쓰지 않는 기준 이미지는 내려받지 않는다. 공통 원본은 한 번 검사하고 모든 사용 위치를 표시한다. 동영상 대표 이미지와 실제 동영상은 별도 항목으로 확인한다. 장면 하나의 연결이 잘못되어도 다른 장면의 자료 검사를 이어 간다.

이미지는 실제 원본 디코딩과 캔버스 읽기를 확인하고 출력용 이미지 연결도 확인한다. 동영상은 기존 출력 디코더를 사용해 현재 재생 구간의 시작·중간·마지막 대표 프레임과 실제 원본 길이를 검사한다. 녹음과 음악은 출력과 같은 AudioContext·MPEG-4 오디오 디코더를 사용하고 선택 녹음의 실제 길이가 사용할 원본 구간을 담는지 확인한다. 클라우드 원본·동영상 대표 이미지는 저장 키로 새 접근 경로를 읽고, 네이티브 원본은 실제 보관 경로를 읽는다. 현재 탭에 남은 저장 키 없는 이미지 원본은 등록된 inline 바이트를 사용한다. 녹음이 없는 장면은 문제로 처리하지 않는다.

파일 문제를 모아 장면·썸네일·음악 편집으로 이동하고 자료 점검으로 돌아오면 결과와 초점을 복원한다. 실패한 자료만 재검사하면 기존 통과 파일은 다시 읽지 않는다. 전체 다시 점검은 모든 자료를 새로 읽는다. 검사 중단·프로젝트 전환·자료 선택이나 원본·사용 구간 변경은 늦은 검사 결과를 완료로 반영하지 않는다. 서명 URL의 갱신과 무관한 제목 변경은 재검사를 요구하지 않으며 원본 inline 내용의 변경은 감지한다. 큰 이미지 문자열을 검사 식별 문자열에 직렬화하지 않고 기존 문자열 참조와 작은 메타데이터를 비교한다. 파일별 60초 제한과 사용자 중단을 지원하고 이미지 URL·영상 입력·오디오 컨텍스트를 정리한다. MPEG-4 오디오 디코더에는 선택적인 중단 신호를 추가해 검사 취소 뒤 디코딩을 계속하지 않게 했다. 기존 출력 호출 방식과 영상·음성 구성은 유지한다.

검사는 읽기 전용이며 결과는 프로젝트별 메모리에 보관한다. 저장·업로드·편집 이력을 만들지 않고 새로고침 시 초기화한다. 첫 구현은 명시적인 사전 점검 버튼과 문제 목록이며 MP4 버튼을 점검 상태로 차단하지 않는다. 대표 프레임 검사는 전체 영상 프레임 검증이나 인코딩 지원 보증이 아니며 점검 후 외부 파일 상태가 바뀔 수 있다. 기존 MP4 출력은 계속 실제 파일을 읽고 디코딩·인코딩 오류를 처리한다. 새 SQL·저장 형식·네이티브 명령·API 키가 필요하지 않으며 API 음성 생성·키 입력 UI는 기본 숨김을 유지한다.

검증은 **61개 파일의 401개 테스트와 운영 빌드**를 통과했다. v1·2.0·2.1의 실제 사용 자료 집계·중복 제거, 선택 녹음·합친 구간·분할 원본, 동영상 대표 이미지·앞 이미지·보조 이미지와 프레임 위치, 실제 원본 길이 부족·디코딩 실패, 서명 URL 갱신·inline 내용 변경·큰 이미지 식별 크기, 파일 문제 수집·실패만 재검사, 편집 이동·결과 유지·초점 복원·프로젝트 격리·검사 중 편집·중단과 늦은 결과 무시를 확인했다. 이미지 URL·영상 입력·오디오 컨텍스트 정리와 MPEG-4 중단도 검증했다.

실제 Chromium에서는 이미지 50개·MP4 1개·WAV 3개를 보관한 7개 장면의 프로젝트를 사용했다. 실제 출력에 쓰는 **14개 검사 항목**에서 손상 PNG·누락 MP4·손상 음악을 함께 검출했고, 공통 동영상의 두 장면 위치를 표시했다. 실패한 장면 편집·복귀 후 재검사는 **실패 자료 3개를 각 1회만** 읽었다. 검사만 수행할 때 IndexedDB 쓰기는 0회였고, 실제 중단·선택 변경에 따른 재검사·1440px와 1080px 화면·새로고침 후 결과 초기화를 확인했다. 선택 변경 후 공통 이미지가 하나로 합쳐져 13개 검사 항목을 통과했다. 이어서 완료 화면에서 MP4를 실제 생성·재생 디코딩했으며 **465프레임·31초**, AAC 길이는 약 **31.0451초**로 한 프레임 이내 차이였다. ZIP의 **원본 54개 SHA-256이 전부 일치**했고 원문과 합친 녹음 구간을 보존했다. 생성 API 호출·페이지 오류는 0개였다. 운영 Supabase/R2 실제 읽기와 패키징한 Tauri 앱은 별도 검증 범위이며 저장 키·네이티브 분기는 모의 검증과 구분한다.


**H6의 장면 이미지 제작 프롬프트 묶음을 구현했다.** 전체 검토에서 기본 접힘 패널을 열고 화면 미선택 장면·전체 장면 또는 개별 장면을 선택한다. 현재 공통 프롬프트 조합 함수를 재사용해 최신 인물 외형·구도·장면 내용·공통 스타일을 메인 이미지 프롬프트에 반영하고 현재 장면 순서대로 미리보기·일괄 복사·UTF-8 TXT 다운로드를 제공한다. 저장된 오래된 `full_prompt`를 그대로 내보내지 않는다. 인물 기준 이미지의 실제 첨부와 외부 이미지 제작은 사용자가 수행하며 이번 묶음은 장면 메인 이미지 프롬프트를 다룬다.

선택은 프로젝트별 메모리에서 고정 장면 ID로 관리한다. 장면 편집·이동과 다른 프로젝트를 오간 뒤에도 선택을 유지하며 새로고침하면 초기화한다. 장면이 합쳐져 사라지거나 이미지 내용이 비면 묶음에서 제외하고 알린다. 같은 표시 번호를 받은 다른 장면을 대신 선택하지 않는다. 동영상·합친 화면도 현재 화면 있음으로 판정하고 구성을 읽지 못하는 장면은 미선택으로 추측하지 않는다. 복사·다운로드 뒤 선택·프롬프트·인물 외형·스타일 등 내보낼 내용이 달라지면 최신 묶음을 다시 내보내도록 안내한다. 클립보드 거부 시 읽기 전용 미리보기를 선택해 직접 복사하거나 TXT를 사용할 수 있다. 지연된 복사 응답이 이전 내용을 최신 묶음으로 표시하지 않게 했다.

권장 이미지 파일명은 `scene_02__g100[프로젝트토큰.장면토큰].png` 형태로 프로젝트·장면의 고정 ID를 base64url로 담는다. 영문·숫자·이식 가능한 구분자를 사용하고 실제 이미지 형식에 맞춰 확장자를 바꿀 수 있다. 일괄 배치는 이 식별 정보를 일반 번호 추론보다 먼저 읽어 순서 변경 후에도 같은 장면에 연결안을 제안한다. 다른 프로젝트·없어진 장면·손상되거나 여러 개 있는 식별 정보는 미연결로 남기고 예전 번호로 우회하지 않는다. 식별 부분이 없는 기존 파일명은 현재 번호 기반 제안을 유지한다. 기존 파일 검증·연결안 확인·명시적인 적용·기존 화면 유지·부분 실패 재시도·편집 취소를 재사용한다.

묶음 조회·선택·복사·TXT 내보내기는 읽기 전용이며 이미지 원본 다운로드·API 호출·프로젝트 저장·편집 이력을 만들지 않는다. 실제 이미지 적용 시에만 기존 업로드·저장 경로를 사용한다. 편집 형식·SQL·저장 RPC·네이티브 명령·렌더러는 변경하지 않았고 API 키 입력과 음성 생성 UI는 기본 숨김을 유지한다.

검증은 **64개 파일의 424개 테스트와 운영 빌드**를 통과했다. v1·2.0·2.1의 최신 프롬프트 조합·순서·원문 불변, 공통 외형·스타일 적용, 미선택·동영상·합친 구간·손상 구성 구분, 빈 내용·없어진 장면 제외, 편집·순서 변경·프로젝트 격리와 선택 복원, 클립보드 실패·지연 응답·TXT 호출을 확인했다. 파일명은 순서 변경·유니코드와 분할 장면 ID·PNG/JPEG/WebP 확장자·중복 다운로드 접미사·다른 프로젝트·장면 소실·중복 ID·손상·중복 식별자·기존 번호 제안을 검증했고 일괄 배치와 실제 장면 연결도 회귀 테스트했다.

실제 Chromium에서는 8개 장면을 합친 7개 장면과 원본 53개를 사용했다. 화면 미선택 두 장면과 동영상 한 장면을 골라 실제 클립보드 내용·UTF-8 TXT 바이트와 표시된 묶음의 일치를 확인하고 클립보드 실패를 모의해 직접 복사 안내·선택을 확인했다. 묶음 조회·선택·내보내기 중 원본 저장소 읽기와 IndexedDB 쓰기는 0회였고 저장 JSON·수정 시각이 유지됐다. 선택한 장면의 프롬프트 수정·순서 변경 후 최신 내용과 선택 ID를 유지했다. 별도 장면 합치기로 선택 대상이 사라지면 제외하고 같은 번호의 새 장면을 고르지 않았다. 이전 권장 파일명으로 만든 실제 PNG·JPEG·WebP 3개는 현재 Scene 3·2·4의 원래 ID로 연결됐고 다른 프로젝트·없어진 장면·손상 파일명 3개는 미연결로 남았다. 적용·취소·다시 실행·재열기·전체 영상 미리보기에서 기존 동영상의 앞 이미지·트림과 합친 녹음 구간을 유지했다. ZIP의 **기존 원본 53개와 새 이미지 3개 SHA-256이 전부 일치**했고 원본 56개와 제작안을 보존했다. 1440px·1080px에서 패널 너비를 확인했으며 생성 API 호출·페이지 오류는 0개였다. 운영 Supabase/R2 실제 쓰기와 패키징한 Tauri 앱은 별도 검증 범위다.


**H7의 내레이션 파일 일괄 배치를 구현했다.** 전체 검토에서 MP3·WAV·M4A·MP4·WebM을 각 30MB·120초, 최대 40개·합계 120MB까지 준비한다. 기존 파일 검사와 실제 오디오 디코딩으로 길이를 확인하고 새 녹음 미리듣기·연결 장면·현재 길이·기존 녹음 유무를 표시한다. 기존 녹음은 사용자가 듣기를 누를 때 읽으며 합친 장면의 여러 녹음 구간도 비교할 수 있다. H6의 고정 프로젝트·장면 식별 파일명과 기존 번호 기반 제안을 재사용한다. 준비·연결안 변경만으로는 파일 업로드나 프로젝트 저장을 하지 않는다.

기본값은 기존 녹음 유지이며, 명시적으로 교체하면 분할·합친 장면을 포함한 대상 장면의 모든 녹음 구간을 파일 하나로 바꾼다. 같은 장면에는 파일 하나만 허용하고 중복·미연결·손상 파일을 제외한다. 일반 일괄 적용은 현재 장면 길이에 들어가는 파일만 처리한다. 긴 파일은 별도 시간 조정 검토에서 장면·전체 영상·뒤 장면·자막의 전후를 보여 주고 자막 유지 또는 비율 재배치를 선택해 개별 확정한다. 녹음과 시간 변경은 같은 편집 이력으로 취소·복원하며 실제 발화 정렬을 제공하지 않는다.

적용 직전과 파일 저장 후 최신 고정 장면 ID·대본·상대 자막 시간·녹음·장면 구조를 다시 확인한다. 단순 순서 변경은 같은 장면 ID에 적용할 수 있지만 대본·길이·녹음·구조가 바뀌면 덮어쓰지 않고 새 원본을 보관한다. 긴 녹음의 시간 조정은 전체 시간표도 다시 확인한다. 저장이 완료된 파일과 처음 사용한 장면 ID를 목록에 보관해 재시도하거나 다른 장면에 연결할 때 재업로드하지 않는다. 원래 장면이 사라져도 최초 IndexedDB 키·경로·저장 키를 유지하며, 공통 녹음 자료 생성 함수를 분리해 일반 자료 수집과 같은 계약을 사용한다.

파일별 부분 실패·실패한 녹음만 재시도·현재 파일 완료 후 중단을 지원한다. 완료한 항목은 재처리하지 않고, 프로젝트 저장만 실패하면 기존 상단 저장 재시도를 사용한다. 목록은 앱을 열어 둔 동안 프로젝트별로 유지하며 목록 제거는 원본 삭제를 하지 않는다. 파일 적용 중 새로고침·프로젝트 삭제·로그아웃·페이지 이탈을 기존 저장 흐름과 함께 보호하고 다른 화면에서도 진행 상태와 중단 버튼을 제공한다. 임시 파일 미리보기 URL은 목록 제거·종료 시 해제한다. 편집 형식·SQL·저장 RPC·네이티브 명령·렌더러는 변경하지 않았고 API 키 입력과 API 음성 생성 UI는 기본 숨김이다.

검증은 **66개 파일의 444개 테스트와 운영 빌드**를 통과했다. v1·2.0·2.1의 적용·원문·화면·시간 보존, 합친 녹음 유지·명시적 교체·취소·복원, 긴 파일 검토·자막 재배치·전체 시간표 변경 차단, 중복·미연결·손상·상한 검사, 부분 실패·저장 재시도·중단 후 재개를 확인했다. 저장 중 순서 변경·대본 수정·장면 합치기 이후 늦게 도착한 파일의 원본 보관과 재사용, 다른 장면으로 연결한 녹음의 실제 IndexedDB 재열기·원래 키·ZIP 바이트도 검증했다.

실제 Chromium에서는 기존 원본 54개와 7개 장면을 사용해 WAV 7개를 검사했다. 준비 중 파일·프로젝트 쓰기는 0회였고, 기존 합친 녹음 두 구간의 6초 미리듣기를 확인했다. 파일 저장 실패 1회와 프로젝트 저장 실패 1회를 각각 모의하고 파일 저장 시도 5회로 새 원본 4개를 저장했다. 프로젝트 재시도는 파일을 다시 저장하지 않았으며, 실패한 녹음만 재시도했다. 3초 장면에 4.2초 녹음을 적용해 뒤 장면·자막을 함께 이동하고 취소·복원을 확인했다. 합친 녹음 교체를 취소하면 기존 두 구간이 복원됐으며 목록을 비운 뒤에도 새 원본이 유지됐다. 실제 MP4는 **32.2초·483프레임**으로 계획과 일치했고 오디오·동영상 길이 차이는 1프레임 미만이었다. 오디오와 동영상 프레임을 디코딩했으며 ZIP의 **기존 원본 54개와 새 녹음 4개 SHA-256이 모두 일치**했다. 재열기·제작안 보존·1440px·1080px 화면을 확인했고 생성 API 호출과 페이지 오류는 0개였다. 운영 Supabase/R2 실제 쓰기와 패키징한 Tauri 앱은 별도 검증 범위다.


**H8의 내레이션 대본 묶음 내보내기를 구현했다.** 전체 검토에서 기본 접힘 패널을 열고 녹음 연결이 없는 장면·전체 대본 또는 개별 장면을 선택한다. 기존 장면 내레이션 패널과 같은 대본 함수를 사용해 현재 편집한 captions를 순서대로 읽으며 자막 배열이 없는 형식은 현재 narration·caption을 사용한다. 오래된 원문으로 되돌리지 않고 현재 장면 순서로 제목·길이·글자 수·녹음 연결 구간 수와 대본을 표시한다. 현재 자막이 비어 있으면 이전 대본으로 대체하지 않고 제외한다. 길이가 잘못된 장면은 확인 필요로 표시하고 유효한 대본은 내보낼 수 있다. 장면 길이가 실제 낭독 시간의 예측값이 아님을 안내한다.

대본 일괄 복사·UTF-8 TXT 다운로드와 직접 복사할 수 있는 읽기 전용 묶음을 제공한다. 안내와 파일명 대신 각 장면의 ‘낭독할 대본’만 녹음하도록 구분한다. 권장 WAV 파일명은 H6의 동일한 프로젝트·장면 식별자를 재사용하며 실제 형식에 따라 MP3·M4A·MP4·WebM 확장자로 바꿀 수 있다. 외부에서 준비한 파일은 H7 일괄 배치의 연결안 검토·파일 검사·명시적 적용·기존 녹음 유지·시간 조정·편집 취소 경로를 사용한다. 다른 프로젝트·없어진 장면·손상 식별자는 번호로 추측하지 않는다.

선택은 고정 장면 ID로 프로젝트별 메모리에 보관하며 편집 화면을 다녀오거나 순서를 바꿔도 유지한다. 삭제·합치기로 없어진 선택과 빈 대본은 안내 후 제외한다. 이미지 프롬프트와 대본은 공통 선택 훅을 독립적으로 사용해 서로의 선택을 바꾸지 않는다. 복사·다운로드한 내용과 최신 묶음을 비교하고 선택·대본·길이·순서·녹음 연결 정보가 바뀌면 최신 묶음을 다시 내보내도록 안내한다. 지연된 클립보드 응답도 예전 묶음을 최신으로 표시하지 않는다. 클립보드 실패 시 전체 묶음에 초점·텍스트 선택을 제공하며 TXT 실패도 성공으로 표시하지 않는다.

녹음 연결은 실제 장면 구성의 구간을 읽어 분할·합친 녹음을 포함하고, 읽지 못하는 구성은 녹음 없음으로 자동 선택하지 않는다. 이 상태는 편집 정보 기준이며 실제 원본 가용성 검사는 H5 자료 점검을 사용한다. 대본 조회·선택·복사·다운로드는 원본 파일 읽기·API 호출·프로젝트 저장·편집 이력을 만들지 않는다. 새로고침하면 선택 목록은 초기화한다. 편집 형식·SQL·저장 RPC·네이티브 명령·렌더러는 변경하지 않았고 API 키 입력과 API 음성 생성 UI는 기본 숨김을 유지한다.

검증은 **68개 파일의 466개 테스트와 운영 빌드**를 통과했다. 실제 v1 파서·v2.0·v2.1의 최신 대본·원문 불변·장면 순서·길이, 자막 순서·줄바꿈·긴 외부 제작 대본, 빈 대본·없어진 선택·잘못된 길이 표시, 합친·나눈 녹음 구간·연결 없는 보관 원본·손상 구성 구분을 확인했다. 권장 파일명은 유니코드·분할 ID·지원 오디오 확장자 5개·중복 다운로드 접미사·순서 변경·다른 프로젝트·없어진 장면을 검증했다. UI는 기본 접힘·녹음 없는 장면 선택·개별·전체·해제, 복사·TXT·실패 복구·지연 응답, 편집·순서 변경·합치기 후 선택 유지와 제외, 이미지 선택 독립·프로젝트 격리를 확인했다. 공통 선택 훅을 사용하는 기존 이미지 프롬프트 기능도 회귀 검증했다.

실제 Chromium에서는 기존 원본 54개와 7개 장면을 사용했다. 녹음 없는 장면 6개와 개별 장면을 고르고 실제 클립보드와 UTF-8 TXT 바이트가 표시된 묶음과 일치하는지 확인했다. 클립보드 실패를 모의해 전체 텍스트 선택을 확인했으며 이미지 프롬프트 선택과 대본 선택이 서로 독립적이었다. 대본 조회·선택·내보내기 중 원본 저장소 읽기와 IndexedDB 쓰기는 0회였고 프로젝트 JSON·수정 시각·편집 이력을 유지했다. 자막 편집·순서 변경 후 최신 문구·선택 ID를 유지했고, 추가로 합쳐져 없어진 선택은 제외했다. 이전 권장 파일명으로 만든 WAV 3개는 순서 변경 후에도 원래 장면 ID에 연결됐고 다른 프로젝트·없어진 장면·손상 식별자 파일 3개는 미연결로 남았다. 실제 디코딩·연결 적용·취소·다시 실행·전체 미리보기·재열기를 확인했고 동영상 트림·앞 이미지·보조 화면과 기존 합친 녹음 두 구간을 유지했다. ZIP의 **기존 원본 54개와 새 녹음 3개 SHA-256이 모두 일치**했으며 원본 57개와 제작안을 보존했다. 1440px·1080px에서 패널 너비를 확인했고 생성 API 호출·페이지 오류는 0개였다. 이번 변경은 렌더러를 수정하지 않았으며 운영 Supabase/R2 실제 쓰기와 패키징한 Tauri 앱은 별도 검증 범위다.


**자막 편집 후 미리보기·출력 차단을 수정했다.** APP_DATA를 처음 불러올 때 사용하는 narration/captions 문구 유사도 검사가 현재 편집본에도 적용돼, 자막을 크게 고친 뒤 `captions가 narration 내용을 충분히 포함하지 않습니다` 오류로 미리보기·완료 단계·MP4가 차단됐다. 편집한 자막을 대본으로 읽는 내레이션 패널·H8 묶음과 출력 검사의 기준도 달랐다. 입력 제작안의 문구 유사도 검사는 유지하고 편집본에서는 현재 자막의 내용·시간·구조를 검사하도록 범위를 바로잡았다. 과거 narration이나 원본 제작안을 새 자막으로 덮어쓰지 않으며 별도 변환·편집 버전·SQL 변경은 없다.

빈 자막·잘못된 시작/종료·장면 범위 이탈·겹침·중복 ID·핵심 업적 연결·자료 원본 보호 등 기존 검사는 유지한다. 기존 녹음을 자동 교체하거나 자막에 정렬하지 않는다. 이미 구현된 AI 음성의 문구 불일치 안내와 지연 응답 적용 차단도 유지한다. API 키 입력과 API 음성 생성 UI는 기본 숨김이다.

수정 전 추가한 회귀 테스트 4건이 동일한 유사도 오류와 완료 버튼 차단으로 실패하는 것을 확인했다. 수정 후 **68개 파일의 471개 테스트와 운영 빌드**를 통과했다. 녹음 유무에 따른 완전한 문구 교체·영상 계획·대본 복사·묶음 반영·원문 보존, 입력 제작안의 불일치 거부, 빈 자막·시간 오류·겹침 차단, 합친 장면의 새 자막·분할·취소·복원·JSON 재열기를 검증했다. 실제 앱 테스트에서도 큰 문구 수정 후 녹음을 보존하고 대본 복사·묶음·취소·복원·완료 화면의 MP4 생성 버튼까지 이어지는지 확인했다.

실제 Chromium에서는 원본 54개가 있는 7개 장면에서 합친 첫 장면의 자막 두 개와 동영상 장면의 자막 하나를 완전히 다른 문장으로 바꿨다. 장면·전체 미리보기, 실행 취소·다시 실행, 실제 클립보드·UTF-8 TXT의 최신 대본, 저장·재열기와 완료 화면의 MP4 생성을 통과했다. 잘못된 자막 종료 시각은 완료를 차단하고 수정하면 다시 진행됐다. 원본 제작안을 복사해 불일치 자막을 넣은 입력은 계속 거부됐다. 실제 렌더링의 글자 그리기를 관찰해 새 문장 세 개가 그려지고 이전 두 문장은 출력되지 않는지 확인했다. MP4는 **31초·465프레임**으로 계획과 일치했고 AAC 오디오 길이 차이는 약 **0.0451초**, 1프레임 미만이었다. 오디오와 영상 프레임을 디코딩했으며 MP4 포함 ZIP의 **기존 원본 54개 SHA-256이 모두 일치**했다. 원문·이전 narration 메타데이터·합친 녹음 두 구간·동영상 트림·앞 이미지·보조 화면과 편집 형식 5를 보존했다. 자막 편집 중 오디오·영상 원본 저장소 쓰기는 0회였으며 API 호출·페이지 오류도 0개였다. 운영 Supabase/R2의 실제 쓰기와 패키징한 Tauri 앱 검증은 이번 범위에 포함하지 않는다.
