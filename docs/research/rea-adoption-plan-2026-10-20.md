# Great100 Studio의 REA 역공학 적용 계획

2026년 10월 20일 작성. [서비스 선정 조사](rea-service-selection-2026-10-20.md)와 [REA 검증 기록](rea-service-evidence-2026-10-20.json)을 바탕으로 작업 범위와 완료 기준을 정리했다. A 기준 이미지 처리와 B 편집 이력은 구현·검증을 완료했다. [첫 적용 결과](rea-first-release-2026-10-20.md)에 실제 검증 범위와 남은 한계를 기록했다. C 편집 검증·형식 호환, D 공통 시간 계산·내레이션 길이 연동, E 자료 목록·구간 구성, F1 순서 변경·F2 나누기·F3 인접 장면 합치기는 아래 구현 결과를 참고한다. G~H는 후속 작업이다.

**첫 적용 묶음은 업로드한 인물 기준 이미지의 참조 전달과 편집 실행 취소로 잡는다.** Vrew에서는 자막·클립·편집 명령의 동작을 분석하고, Great100에는 작은 변경부터 적용한다. 이후 시간 연동을 정리한 뒤 장면 나누기·합치기, 내레이션 자동화, 전체 장면 검토와 일괄 생성으로 확장한다.

| 단계 | 역공학에서 확인할 내용 | Great100에 적용할 결과 | 선행 조건과 완료 기준 |
| --- | --- | --- | --- |
| 0 | Vrew의 자막 편집, 클립 시간, 실행 취소, 장면 조작 | 동작 비교표와 편집 데이터·명령 연결표 | 확보한 코드의 근거와 실제 동작을 구분한다. 미확인 동작은 Great100의 설계 선택으로 명시한다. |

| 3 | 문장·자막·장면의 시간 관계 | 음성 길이에 맞춘 장면 조정, 공통 시간 계산, 편집용 검증 | 원본 제작안과 편집 상태를 구분하고 미리보기·출력의 시간 계산을 통일한다. |
| 4 | 장면 순서 변경, 분할·병합 후 자료와 음성의 처리 | 순서 변경 → 자막 경계에서 나누기 → 인접 장면 합치기 | 안정적인 자료 ID와 구간 단위 화면·음성 참조가 필요하다. |
| 5 | Fliki·Vrew의 대본 수정 이후 음성·자막 갱신 과정 | 장면별 TTS, 수정한 장면 재생성, 정렬 결과 검토 | 공급자의 한국어·타임스탬프·비용·응답 형식을 작은 표본으로 검증한다. |
| 6 | Mootion의 전체 장면 검토와 선택적 재생성 | 장면 보드, 미선택·오류 필터, 생성 결과 비교와 부분 재시도 | 단계 2의 편집 처리와 단계 4의 자료 참조 구조를 재사용한다. |

첫 배포 범위는 **단계 1과 2**다. 단계 0은 구현 판단에 필요한 조사 범위를 한정한다. 단계 3 이후에는 프로젝트 데이터와 출력 동작에 대한 변화가 커지므로 각각 독립된 작업으로 검증한다.

**현재 구조에서 먼저 해결해야 할 연결 관계가 있다.** 단순한 UI 추가로 처리하면 다음 문제가 생긴다.

| 코드에서 확인한 사실 | 구현에 주는 제약 |
| --- | --- |
| 장면·썸네일 생성이 `mode === "openai"`인 기준 이미지만 전달한다. | 업로드 이미지도 실제 원본을 읽는 공통 경로가 필요하다. URL을 그대로 API에 보내는 방식으로는 해결되지 않는다. |
| `persist`가 오래된 콜백의 변경을 `mergeProjectChanges`로 병합한다. | 실행 취소도 최신 상태에 특정 필드의 역변경을 적용해야 한다. 과거 프로젝트 전체를 복구하면 새로 완료된 업로드를 잃을 수 있다. |
| ID가 있는 배열의 병합은 현재 배열의 순서를 유지한다. | 장면 재정렬에는 순서를 명시적으로 바꾸는 연산이 필요하다. 배열 순서만 바꿔 기존 저장 함수에 넣는 접근은 부족하다. |
| APP_DATA 검증이 `scene_01` 형식의 ID·순서와 핵심 업적의 장면 연결을 요구한다. | 원본 입력 검증과 편집된 프로젝트 검증을 분리해야 자유로운 분할·병합이 가능하다. |
| 자막에는 안정적인 ID가 없고 시간은 본문 기준 절대 초다. | 초기 이력은 장면 ID와 자막 배열 단위로 기록한다. 구조 편집 도입 전에는 자막에도 안정적인 ID가 필요하다. |
| Tauri의 녹음·동영상 읽기가 장면 번호를 경로로 사용한다. | 표시 순서와 저장 위치를 분리해야 장면 이동 후에도 같은 원본을 읽는다. |
| 클라우드는 저장 후 더 이상 참조되지 않는 파일을 제거한다. | 장면을 제거하거나 합칠 때 실행 취소가 필요한 원본을 유지하는 자료 목록이 필요하다. |
| 한 장면의 녹음은 파일 하나이며 화면도 제한된 조합을 사용한다. | 두 장면을 합치려면 이미지·영상·음성의 내부 구간을 보존할 수 있어야 한다. |
| 완성 MP4는 프로젝트 수정 시각과 렌더 버전으로 유효성을 판단한다. | 실행 취소·시간 변경도 새 편집으로 저장하고 출력 갱신 상태에 반영해야 한다. |

**단계 0에서는 기능별로 답이 필요한 질문만 추적한다.** 이미 확보한 Vrew JS 3개와 기존 Evidence를 먼저 사용한다. 같은 자료의 전체 분석을 반복하기보다 관련 모듈·소스 위치를 조회하고, 부족한 직접 의존성만 추가 확보한다. 파일이 바뀌면 기존 SHA-256과 구분해 다른 자료 묶음으로 기록한다.

| 조사 질문 | 관찰할 행동 | 남길 결과 |
| --- | --- | --- |
| 문구와 내레이션은 어떻게 연결되는가? | 자막 한 줄 또는 대본 한 문장을 수정한다. | 바뀐 필드, 음성 재생성 여부, 다른 자막·장면에 미치는 영향 |
| 자막 경계의 시간 규칙은 무엇인가? | 시작·종료 손잡이를 이동하고 인접 자막에 접근한다. | 최소 길이, 겹침 처리, 시간 단위, 재생 위치 변화 |
| 실행 취소 한 번의 단위는 무엇인가? | 한 번 드래그, 연속 타이핑, 후보 변경 후 실행 취소한다. | 묶음 기준과 다시 실행 상태 |
| 비동기 결과는 어떻게 보존되는가? | 생성·업로드가 진행되는 동안 다른 편집을 한다. | 늦게 도착한 결과와 사용자 편집의 병합 방식 |
| 장면 경계를 바꾸면 무엇이 이동하는가? | 순서 변경, 자막 경계에서 분할, 인접 장면 병합을 한다. | ID, 자료 참조, 음성 구간, 자막·재생 위치의 변화 |
| 참조 이미지와 촬영 지시는 어떻게 구분되는가? | 같은 인물 참조에 다른 구도·장소를 지정한다. | UI 설정과 관찰 가능한 요청 필드·결과의 관계 |

각 결과는 행동 이전 상태, 행동, 이후 상태, 근거 소스 위치 또는 Evidence ID, 적용할 Great100 규칙으로 연결한다. 정적 코드의 후보 경로와 런타임 결과를 별도로 표시한다. 이번 표본에서 확인된 `mergeClips`, `undoAction`, `redoAction` 등은 조사 진입점이며 구현 규칙이 확인된 상태는 아니다.

런타임은 사용할 수 있는 브라우저의 해당 체험판이나 공식 앱으로 관찰한다. 계정·생성 한도 등으로 관찰이 어려운 질문은 미확인으로 남기고, Great100에서 필요한 동작을 명시해 자체 테스트한다. 조사 산출물은 여섯 질문에 대한 동작표와 다음 구현에 필요한 데이터·명령 연결표다. 서버의 생성 모델을 복원하는 작업은 이 계획의 구현 의존성이 아니다.

**단계 1은 기준 이미지 원본을 읽는 경로를 통일한다.** `mode` 대신 선택한 후보의 종류와 실제 자료를 기준으로 참조 가능 여부를 판단한다. 업로드 이미지와 생성 이미지를 모두 처리하며, mock SVG는 생성 참조 대상에서 제외한다.

새 공통 함수 `resolveReferenceImage(project, candidate)`를 제안한다. R2의 저장 키, IndexedDB 자료, 데스크톱 파일, 아직 저장 중인 data URL 등 현재 저장 상태에 맞게 원본을 읽고, 지원되는 PNG·JPEG·WebP의 base64 데이터로 변환한다. 웹 API의 기존 3MB 참조 제한과 전체 요청 크기를 고려해 참조용 사본을 축소·압축한다. 프로젝트에 보관한 원본은 유지한다.

이 함수를 장면과 썸네일 생성에 연결한다. 보조 이미지에는 인물이 등장하지 않을 수도 있으므로, 기준 이미지 적용은 사용자가 고를 수 있게 다음 UI 작업에서 다룬다. 참조 원본을 읽지 못했으면 생성 요청 전에 재시도 가능한 오류를 표시한다.

변경 예상 위치는 `App.tsx`, `platform.ts`, 새 `reference-image.ts`, `api/generate.ts`, 필요한 Tauri 파일 읽기·요청 검증이다. 완료 기준은 다음과 같다.

- 업로드·생성한 기준 이미지가 같은 참조 전달 경로를 사용한다.
- 로컬 웹과 계정 저장에서 새로고침 후에도 선택한 참조를 읽는다.
- 장면·썸네일 요청에 실제 이미지 데이터가 포함되고 MIME·크기 제한을 만족한다.
- 형식 오류, 과도한 크기, 원본 읽기 실패가 생성 요청 전에 처리된다.
- 모의 응답으로 요청 형식을 확인하고, 실제 이미지 일관성은 동일한 참조와 서로 다른 구도의 소수 장면으로 별도 평가한다.

**단계 2는 편집 명령과 저장을 연결한다.** 우선 지원할 동작은 자막 문구·시간, 자막 시간 초기화, 후보 선택, 장면 프롬프트, 이미지 효과, 음악 볼륨, 현재 제공하는 화면 전환·트림 설정이다.

새 `editor-commands.ts`와 `useEditorHistory.ts`를 제안한다. 명령에는 프로젝트 ID, 장면·자료 ID, 대상 필드, 변경 전후 값과 묶음 ID를 담는다. 실행 취소는 최신 프로젝트에서 해당 필드만 역변경한다. 대상이 남아 있고 현재 값이 명령의 적용 후 값과 일치하는지 검사해, 같은 필드에 도착한 다른 변경을 덮어쓰지 않게 한다. 저장 버전, 서명 URL, 생성 중 상태 등은 사용자 편집 이력과 분리한다. 명령 적용 결과를 기존 저장 큐와 충돌 처리로 전달한다.

첫 구현의 이력은 프로젝트를 열어 둔 동안 최근 50개 편집 묶음으로 제한한다. 같은 프로젝트의 제작 단계 이동은 이력을 유지하고, 다른 프로젝트를 열거나 서버의 최신 작업으로 교체하면 초기화한다. 한 번의 드래그는 한 묶음으로 기록한다. 연속 타이핑은 같은 입력란에서 묶되 한글 IME 조합 완료를 고려한다. 실행 취소 후 새 편집을 하면 다시 실행 목록은 비운다.

입력란 내부에서는 브라우저의 텍스트 실행 취소를 사용할 수 있게 전역 단축키를 가로채지 않는다. 도구 모음의 실행 취소 버튼과 입력란 밖의 단축키로 프로젝트 편집을 되돌린다. 버튼에는 다음에 되돌릴 편집 이름을 표시한다.

후보 생성·업로드 완료는 시스템 결과로 반영하므로 자막 실행 취소에 휩쓸리지 않아야 한다. 파일을 실제 삭제하는 동작은 첫 이력 범위에 넣지 않는다. 삭제된 자료를 참조하는 이전 이력은 무효화하고 안내해, 실행 취소가 존재하지 않는 파일을 선택하지 않게 한다. 저장 실패 시 편집본과 이력은 유지하고 실패 상태를 보여 주며, 다른 PC의 버전 충돌 시에는 기존 최신 작업 복구 절차를 따른다.

완료 기준은 자막 드래그 한 번이 정확히 한 번에 복구되고, 이미지 생성 완료 이후 자막을 되돌려도 생성 후보가 남으며, 빠른 편집·실행 취소가 클라우드 저장 순서를 깨뜨리지 않는 것이다. 기존 [병합 테스트](../../src/project-changes.test.ts)와 [클라우드 저장 테스트](../../src/cloud.test.ts)에 이 경쟁 상황을 추가한다.

**단계 3은 편집 시간의 기준을 통일한다.** 원본 `source_text`와 `source`는 제작안으로 보관하고, 현재 프로젝트의 순서·문구·시간·자료 참조를 편집 상태로 검증한다. 입력 시의 `validateAppData` 규칙과 출력 가능한 편집 상태의 규칙을 분리한다. 핵심 업적의 시각화와 자막 내용 검사는 편집 후에도 이어가되, 원본 장면 ID의 형식이 편집 기능을 막지 않게 한다.

추가 메타데이터에는 독립적인 `editor_version`을 둔다. APP_DATA의 `schema_version`과 구분해 기존 1·2.0·2.1 프로젝트를 읽는다. 원본 프로젝트 ID는 장면 순서 변경 때문에 재발급하지 않는다. 표시 번호는 순서에서 계산하고, 자막 ID·원본 장면 연결·핵심 업적의 현재 장면 연결을 편집용으로 관리한다.

새 `timeline.ts`는 장면 길이와 자막의 장면 내 상대 시간을 기준으로 계산한다. 내부 계산은 정수 밀리초를 사용하고, 현재 초 단위 필드와는 어댑터로 변환한다. 편집 작업이 확정될 때 뒤 장면의 시작·종료와 절대 자막 시간을 함께 갱신한다. 별도의 절대 시간과 상대 시간을 각각 수정 가능한 원본으로 저장하지 않는다.

기존 프로젝트를 변환할 때는 현재 렌더러가 실제 사용하는 장면 순서·길이와 자막의 장면 내 위치를 보존한다. 원문에 시간 틈이 있던 프로젝트도 변환 전후 미리보기·출력 비교에 포함하고, 원문의 절대 시각은 `source`에 유지한다. 시간 계산을 바꾸는 변환은 수정 전 JSON·자료 백업을 남긴다.

처음 제공할 시간 연동은 **내레이션 길이에 맞추기**다. 현재 업로드 함수는 장면보다 긴 녹음을 거부하므로, 오디오 길이 검사와 파일 저장을 분리해 길이를 읽은 뒤 장면 조정안을 먼저 보여 준다. 읽은 오디오 길이를 수용하도록 장면 길이를 0.1초 단위로 올림하고 기존 1~120초 범위를 검사한다. 기존 자막 시간을 유지할지 비율대로 재배치할지 적용 전에 보여 준다. 자막의 최소 길이·순서·장면 경계가 성립하지 않으면 적용하지 않는다. 이 재배치는 편집 편의 기능이며 실제 단어 타이밍을 인식한 정렬로 표시하지 않는다.

미리보기와 MP4는 같은 시간 계획을 사용한다. 프레임 경계 보정은 공통 함수에서 수행해 장면마다 반올림 오차가 누적되지 않도록 하고, 자막·화면·음성의 주요 경계 차이는 15fps 기준 한 프레임 이내를 완료 기준으로 잡는다. 3초 오프닝과 엔딩의 시간도 같은 검사에 포함한다.

추가 필드가 포함된 프로젝트의 구버전 저장은 자료를 잃을 수 있다. 클라우드 저장 계약에 편집 형식 버전 검사를 포함하고, 기존 파일은 변환 전 사본으로 복구할 수 있게 한다. JSONB 저장·Tauri 직렬화·ZIP 출력이 새 필드를 유지하는지도 검증한다. 필요한 SQL 변경은 이 단계의 호환성 작업에 한정한다.

**단계 4는 자료 ID와 구간 표현을 먼저 도입한 뒤 장면 조작을 연다.** 프로젝트 자료 목록은 원본의 안정적인 ID, 저장 키 또는 실제 경로, 형식·길이를 보관한다. 장면은 그 자료를 참조한다. Tauri는 바뀌는 표시 번호 대신 자료의 저장 위치를 읽도록 바꾸고 기존 번호 기반 폴더는 읽기 호환 경로로 남긴다. ZIP 폴더 이름은 내보내는 시점의 표시 순서로 만들 수 있다.

영상과 음성에는 원본의 시작·종료 구간과 장면 안의 배치 시간을 표현한다. 기존의 주 이미지·동영상·보조 이미지·단일 녹음도 이 공통 구성으로 변환한다. 미리보기와 렌더러가 같은 구간 구성을 읽도록 한 뒤 다음 순서로 제공한다.

1. 순서 변경은 장면 ID·자료·녹음 연결을 유지한 채 표시 번호와 시간을 다시 계산한다.
2. 나누기는 먼저 자막 사이 경계에서 지원한다. 화면과 음성은 원본을 공유하고 사용할 구간만 나눈다.
3. 인접 장면 합치기는 두 장면의 내부 화면 전환과 음성 구간을 순서대로 보존한다. 자막 위치도 새 장면 기준으로 옮긴다.

각 구조 변경은 하나의 실행 취소 단위다. 핵심 업적이 포함된 장면의 연결과 원본 장면의 출처 목록도 함께 갱신한다. 자료 목록은 현재 편집 상태와 실행 취소에 필요한 원본을 유지한다. 장면에서 참조가 사라졌다는 이유만으로 클라우드 파일을 즉시 제거하지 않도록 정리 규칙을 바꾼다.

완료 기준은 이미지·짧은 영상·보조 이미지·녹음이 섞인 프로젝트를 이동·분할·병합하고 되돌린 뒤에도 같은 원본을 읽고 저장·재열기·ZIP·MP4가 일치하는 것이다. 병합 시 두 번째 장면의 이미지나 녹음을 잃는 구현은 이 기준을 충족하지 않는다.

**단계 5의 TTS는 음성 생성과 자막 정렬을 각각 검증한다.** 공급자와 모델은 한국어 표본, 문장·단어 타임스탬프 제공 여부, 비용과 지연, 재시도 동작을 확인한 뒤 선택한다. 타임스탬프가 없으면 강제 정렬의 별도 가능성을 검증하고, 문자 길이 비례 배분은 추정 시간으로 구분한다.

첫 범위는 내레이션 생성·교체, 목소리·속도 선택, 변경한 장면만 재생성이다. 요청 시작 당시의 문구와 옵션을 식별값으로 저장해, 생성 중 문구가 바뀌면 오래된 음성이 현재 편집본을 덮어쓰지 않게 한다. 기존 녹음은 새 음성 생성·저장이 성공한 뒤 교체하고, 자막이나 대본을 바꿨을 때 기존 음성과 불일치를 표시한다. 재시도와 재생성은 각각의 사용량을 추적할 수 있어야 한다.

**단계 6은 전체 장면의 선택과 재시도를 빠르게 만든다.** 한 화면에서 장면의 선택 이미지·동영상, 자막 길이, 녹음 상태를 비교하고 미선택·실패·변경 필요 장면을 모아 본다. 일괄 생성은 장면별 작업 상태와 부분 성공을 저장하며, 실패한 장면만 다시 요청한다. 원래 후보와 새 결과를 함께 보관하고 사용자가 선택을 확정한다. 인물 참조와 구도·장소 지시는 분리해 같은 인물을 다른 장면으로 이어 갈 수 있게 한다.

실제 구현은 다음 작업 단위로 나누는 편이 검토하기 좋다. 각 단위에는 해당 동작의 검증과 회귀 확인을 포함한다.

| 작업 단위 | 주요 변경 예상 위치 | 검토할 핵심 |
| --- | --- | --- |
| A 기준 이미지 원본 처리 | 새 `reference-image.ts`, `platform.ts`, `App.tsx`, API·Tauri 관련 경로 | 저장 모드별 원본 읽기, 크기·형식, 장면·썸네일 연결 |
| B 편집 명령과 이력 | 새 `editor-commands.ts`, `useEditorHistory.ts`, `App.tsx`, 시간·후보 UI | 드래그·IME 묶음, 비동기 결과 보존, 저장 충돌 |
| C 편집 검증과 형식 호환 | `types.ts`, `app-data.ts`, 플랫폼·클라우드·Tauri 저장 | 원본 보관, 안정적인 ID, 새 필드 보존, 구버전 쓰기 |
| D 공통 시간 계산 | 새 `timeline.ts`, `video.ts`, `FullVideoPreview.tsx`, 자막·녹음 UI | 길이 변경, 경계 보정, 오프닝·엔딩, 출력 일치 |
| E 자료 목록과 구간 구성 | 새 자료·구성 어댑터, `types.ts`, `platform.ts`, `cloud.ts`, Rust | 장면 번호와 원본 분리, 자료 보존·정리, 기존 프로젝트 호환 |
| F 장면 구조 편집 | 편집 명령, 장면 목록, 미리보기·출력·ZIP | 순서 변경·나누기·합치기와 실행 취소 |
| G 내레이션 자동화 | 공급자 검증 후 API·음성 처리·자막 정렬 | 오래된 응답 방지, 음성 교체, 시간 정렬, 사용량 |
| H 전체 장면 검토와 생성 큐 | 장면 보드, 후보 관리, 생성·저장 경로 | 선택 유지, 부분 성공, 취소·재시도, 중복 요청 방지 |

A는 자체 코드 근거로 먼저 구현할 수 있다. B는 단계 0에서 확인한 편집 행동을 반영한다. C → D → E → F의 순서로 장면 편집의 기반을 만든다. G는 C·D 이후, H는 B·E의 결과를 사용한다. 과금·대기 시간이 있는 생성 API는 모의 응답으로 일반 검증을 수행하고 실제 품질 확인용 표본과 구분한다.

검증 자료는 세 장면의 짧은 합성 프로젝트와 14~18장면의 대표 제작안으로 구성한다. 자막·녹음이 없는 장면, 짧은 동영상, 보조 이미지, 업로드한 인물 기준 이미지, 생성 중 다른 편집을 수행하는 상황을 포함한다. 기존 v1·2.0·2.1 프로젝트도 불러오기 회귀 자료로 사용하며, 2.0의 기존 출력 제한은 별도로 유지·검증한다.

| 검증 항목 | 통과 기준 |
| --- | --- |
| 이력 | 드래그 한 번은 이력 한 개다. 한글 입력과 다시 실행이 예상한 묶음으로 동작한다. |
| 비동기 작업 | 자막을 되돌려도 완료된 업로드가 남고, 오래된 생성 응답이 새 편집을 덮어쓰지 않는다. |
| 저장 | 로컬·계정 저장에서 새로 열었을 때 편집본이 일치한다. 계정 변경·버전 충돌의 기존 차단이 유지된다. |
| 시간 | 자막·영상·음성의 순서와 범위를 검증하고 주요 미리보기·출력 경계는 한 프레임 이내로 일치한다. |
| 장면 구조 | 재정렬·분할·병합 후에도 원본 자료·음성 구간과 핵심 업적 연결이 보존된다. |
| 내보내기 | ZIP이 편집 상태와 모든 필요한 원본을 포함하고 MP4가 최신 편집을 사용한다. |
| 저장 모드 | 로컬 웹·클라우드·Tauri의 자료 읽기와 쓰기를 각각 검증한다. 실제 실행하지 못한 플랫폼은 미검증으로 표시한다. |

코드 변경 시 관련 Vitest 테스트를 먼저 실행하고 `npm run typecheck`, `npm test`, `npm run build`로 확인한다. Rust 변경에는 사용 가능한 환경의 `cargo check`와 자료 접근 검증을 추가한다. Canvas·인코더를 모의한 테스트에 더해, 시간·미디어 구성 변경은 실제 브라우저에서 만든 MP4의 길이와 대표 경계를 확인한다.

작업 효율은 같은 제작안에서 기준 이미지 준비, 자막 수정, 장면 조정에 필요한 조작 수와 소요 시간을 적용 전후에 기록한다. 개선 폭은 이 비교 후 판단한다. 1080p 출력, 여러 화자, 여러 회차의 인물 라이브러리는 초기 범위의 검증 후 별도 확장으로 다룬다.

**C의 편집 검증과 형식 호환을 구현했다.** 원본 APP_DATA의 장면 번호·순서 검사는 유지하고, 편집 상태에서는 장면·자막 ID, 원본 연결, 현재 핵심 업적 연결, 자막 내용·시간과 장면 길이를 검사한다. `editor_version: 1`은 원본의 `schema_version`과 별개다. 기존 v1·2.0·2.1의 장면 ID·절대 시간·자료 경로를 바꾸지 않으며, 알 수 없는 JSON 필드도 저장·재열기·ZIP에서 보존한다. ZIP에는 v2 원본 `01_source/app_data.json`을 따로 포함한다.

로컬 웹은 IndexedDB 버전 6과 첫 저장 전 사본, 클라우드는 별도 저장 RPC와 버전 강등 차단·원본 보존 트리거·계정별 첫 변환 사본을 사용한다. 구형 클라우드 RPC는 새 형식 필드를 그대로 돌려보내더라도 새 형식의 저장을 거부한다. 운영 배포 전 [편집 호환성 SQL](../../supabase/migrations/202610200001_editor_compatibility.sql)을 먼저 적용해야 한다. SQL 누락 시 구형 함수로 우회하지 않는다. Tauri는 JSON 필드를 그대로 전달하고 업데이트한 네이티브 저장 경로에 버전 검사와 사본 보관을 추가했다. 이 환경에는 Cargo가 없어 Rust 컴파일과 패키징 앱 검증은 남아 있다. 기존 바이너리의 직접 파일 쓰기는 차단하지 못한다.

호환성 테스트는 v1·2.0·2.1 변환, 중복 ID·잘못된 시간·핵심 업적 연결, JSONB의 키 순서 차이, 늦게 도착한 자막 변경, 로컬·클라우드 저장과 ZIP을 다룬다. PGlite의 실제 PostgreSQL 엔진에서 새 SQL의 반복 설치, 첫 변환 사본, 구형 RPC·직접 쓰기의 버전 강등 차단, 원본 교체 거부와 계정별 사본 접근을 확인했다. 실제 Chromium의 로컬 모드에서는 저장소 버전 5의 프로젝트를 열고 자막 편집·실행 취소·다시 실행·새로고침·ZIP 내보내기를 수행했다. 원본·사본·자막 ID와 기존 시간 틈을 유지했고, 미래 형식 저장과 구버전 로컬 읽기를 차단했으며 페이지 오류는 0개였다. 실제 운영 Supabase/R2에 새 SQL을 적용한 검증은 별도다.

**D의 공통 시간 계산과 내레이션 길이 연동을 구현했다.** `timeline.ts`는 정수 밀리초로 장면 길이·장면 내 자막 위치를 계산하고 전체 누적 시각에서 15fps 경계를 정한다. 미리보기와 MP4의 장면·자막·음성·음악이 같은 프레임 계획을 사용한다. 기존 프로젝트를 열 때 시간을 바꾸지 않으며, 녹음 길이 조정을 적용할 때 대상 장면의 길이와 뒤 장면·자막 시간을 함께 갱신한다. 기존 시간 틈과 원본 제작안은 유지한다.

긴 녹음은 검사 후 저장 전에 조정안을 보여 준다. 기존의 짧은 녹음도 길이에 맞출 수 있으며, 자막 시간 유지와 비율 재배치, 장면별·자막별 변경 전후를 비교한다. 최소 자막 길이·겹침·장면 범위·전체 15분 제한을 검사한다. 녹음 끝이 잘리지 않도록 0.1초 단위 길이와 실제 프레임 수를 함께 검사한다. 조정 전체는 실행 취소 한 묶음이며, 업로드한 녹음은 유지한다. 시간을 되돌린 뒤 녹음이 장면보다 길어지면 출력 전에 다시 맞추도록 안내한다. 적용 중 다른 시간 편집이 들어오면 조정안을 다시 확인하게 하며, 이미지 생성처럼 시간과 무관한 늦은 결과는 새 편집과 함께 보존한다.

녹음은 새 ID의 파일로 준비하고 확인 후 연결하므로 조정안 취소·충돌·다른 프로젝트 이동이 기존 파일을 덮어쓰지 않는다. 시간 조정 또는 새 녹음을 처음 적용한 프로젝트만 편집 형식 2로 올린다. 운영 배포 전 [시간 편집 SQL](../../supabase/migrations/202610200002_timeline_editing.sql)을 추가로 적용해야 한다. 별도 RPC와 기존 버전 강등 차단을 사용하며, 첫 전환 전 편집 정보 사본을 로컬·계정·데스크톱에 보관한다. ZIP에는 ID가 붙은 녹음 파일과 표준 이름 사본을 함께 포함한다. Tauri 호출은 새 파일 ID와 기존 파일 읽기를 지원하도록 수정했으나 Cargo가 없어 네이티브 컴파일은 미검증이다.

검증은 39개 파일의 202개 테스트와 운영 빌드를 통과했다. 실제 Chromium에서는 1.1초 장면에 2.23초 WAV를 적용해 2.3초로 늘리고, 자막 비율 재배치·실행 취소·다시 실행·재열기·ZIP을 확인했다. 네이티브 AAC가 없는 이 Chromium에서는 [공식 AAC 확장](https://mediabunny.dev/guide/extensions/aac-encoder)을 필요할 때만 불러오는 경로로 음성 MP4를 완성했다. 실제 결과는 173프레임·11.533333초였으며 예상 프레임 수와 일치했다. AAC 트랙은 11.563537초로 영상과 약 0.030204초 차이였고 한 프레임 이내였다. 장면 경계 전후의 이미지, 두 자막의 화면, 녹음 앞뒤 무음과 끝부분의 음성을 디코딩해 확인했다. 페이지 오류는 0개였다. 클라우드 쓰기·충돌·새 SQL은 모의 저장과 PGlite 범위이며, 실제 운영 계정의 새 SQL 적용·R2·패키징 앱 검증은 별도다.

**E의 자료 목록과 구간 구성을 구현했다.** `media.assets`는 모든 이미지·동영상·녹음·음악에 프로젝트 범위 ID와 원본 경로·계정 키·기존 IndexedDB 위치를 부여한다. 장면의 `composition`은 순서가 있는 화면 구간과 원본 시작·종료·장면 내 배치를 가진 음성 구간을 보관한다. 기존 화면 선택·앞 이미지·트림·보조 이미지·단일 녹음을 어댑터로 변환하며, 미리보기와 MP4가 같은 구성에서 재생 계획을 만든다. 표시 번호 변경은 파일 위치나 자료 ID를 바꾸지 않는다. 데스크톱의 동영상·녹음 읽기도 원본 경로를 전달하도록 수정했다.

원본은 프로젝트를 삭제할 때까지 보관한다. 후보·녹음·음악의 연결 해제와 교체는 원본을 제거하지 않고, 클라우드의 개별 파일 삭제 API도 자료 목록에 보관된 원본·포스터를 거부한다. 새 녹음과 음악은 ID가 붙은 `01_source/media/` 파일을 사용한다. 계정 이전은 편집에서 빠진 원본까지 복사하며, ZIP은 모든 원본과 자료 ID별 경로 목록을 포함하고 현재 표시 번호의 폴더에 선택 파일을 배치한다. 원본 제작안·알 수 없는 메타데이터·기존 파일 경로는 유지한다.

자료가 있는 프로젝트를 저장하면 편집 형식 3으로 전환하고 첫 저장 전 JSON 사본을 보관한다. 별도의 RPC와 원본 자료의 위치 교체·삭제 방지 트리거를 사용하므로 운영 배포 전 [자료 구성 SQL](../../supabase/migrations/202610200003_media_composition.sql)을 추가로 실행해야 한다. 형식 1·2 저장 계약과 구버전 차단을 유지한다. 자료가 없는 프로젝트는 기존 저장 함수를 사용한다.

검증은 41개 파일의 215개 테스트와 운영 빌드를 통과했다. PGlite에서 SQL 반복 적용, 첫 전환 사본, 구형 RPC·직접 쓰기의 원본 삭제·경로 교체 차단, 충돌, 계정별 사본 접근과 프로젝트 삭제 시 정리를 확인했다. 실제 Chromium에서는 번호가 1에서 3으로 바뀐 장면에 두 화면 구간을 넣고 앞 이미지→원본 동영상의 0.4~1.4초 구간→보조 이미지→별도 이미지를 미리보기와 MP4에서 비교했다. 녹음 원본의 0.2~0.7초와 1.2~1.7초를 서로 다른 위치에 배치해 두 음성과 중간 무음을 디코딩했다. MP4는 195프레임·13초로 계획과 일치했고 AAC 차이는 약 0.0264초였다. ZIP에는 원본 8개와 두 화면·두 음성 구간이 남았으며 페이지 오류는 0개였다. 기존 D의 시간 조정·취소·실행 취소·재열기·MP4·ZIP도 실제 브라우저에서 다시 통과했다. 운영 Supabase/R2의 쓰기와 패키징한 Tauri 앱은 별도 검증 대상이며, 이 환경에는 Cargo가 없어 네이티브 컴파일을 확인하지 못했다.

**F1의 장면 순서 변경을 구현했다.** Scene 검토의 순서 앞으로·뒤로 버튼은 최신 프로젝트에서 현재 장면 ID를 찾아 인접 장면과 맞바꾼다. 표시 번호와 장면·자막의 절대 시간을 정수 밀리초로 재계산하며 장면 길이·자막의 장면 내 위치·자료 구성·녹음·핵심 업적 ID·원본 출처와 제작안은 보존한다. 시간 틈이 있던 프로젝트는 이동 시 연속 본문 시간으로 정리하며 실행 취소에서 이전 번호·순서·시간 틈을 복원한다. 선택한 편집 장면은 이동 후에도 유지한다.

배열 순서를 유지하던 저장 병합에는 명시적인 순서 변경만 반영하는 경로를 추가했다. 이동 전 시작한 생성·업로드는 장면 ID로 최신 상태에 병합하고, 늦게 도착한 자막 시간 변경은 현재 장면의 시작 시각으로 옮겨 비교한다. 실행 취소는 전체 장면 스냅샷을 복구하지 않고 순서·번호·시간 필드만 되돌려 새 자료와 다른 편집을 보존한다. 순서 변경 이력은 별도 한 묶음이며 앞서 편집한 자막 이력도 유지한다. 저장 실패 시 새 순서와 이력을 유지해 재시도한다. 기존 편집 형식·저장 RPC를 사용하므로 추가 SQL은 없다.

검증은 43개 파일의 231개 테스트를 통과했다. v1·2.0·2.1, 시간 틈·소수 초·핵심 업적 연결, 이동·실행 취소·다시 실행, 생성·녹음의 늦은 완료, 저장 실패·재시도, 계정 저장의 연속 리비전과 로컬 저장·재열기·ZIP을 확인했다. 실제 Chromium에서는 두 화면·두 음성 구간이 있는 장면을 UI에서 1번→3번으로 옮기고 두 번의 실행 취소·다시 실행·재열기를 수행했다. 선택 장면과 미리보기 1.2초 위치가 유지됐고, 전체 검토와 실제 완료 화면의 MP4 생성이 새 순서와 일치했다. 결과는 195프레임·13초, AAC 차이 약 0.0264초였으며, 이미지·동영상·보조 화면·부분 녹음과 중간 무음을 디코딩해 확인했다. ZIP은 원본 8개, 새 번호의 선택 파일, 두 화면·두 음성 구간과 원본 제작안을 보존했다. 페이지 오류는 0개였다. 운영 Supabase/R2의 실제 쓰기와 패키징한 데스크톱 앱은 별도 검증 범위다.

**F2의 자막 경계 나누기를 구현했다.** APP_DATA 2.1의 다음 자막 시작을 선택해 앞·뒤 길이를 확인하고 각각 1초 이상인 두 장면으로 나눈다. 앞 장면의 ID와 활성 선택을 유지하고 뒤 장면에 독립 ID를 부여하며 표시 번호를 다시 매긴다. 자막 ID·문구·절대 시간·시간 틈, 전체 길이, 원본 제작안과 원본 장면 연결을 보존한다. 핵심 업적 장면을 나누면 양쪽 장면이 그 연결을 이어받는다.

분할 구간은 원본 화면의 재생 시계와 동작 효과 진행률을 보관한다. 앞 이미지→동영상, 원본 트림, 마지막 화면 유지, 보조 이미지의 페이드와 강조 자막이 분할점에서 다시 시작하지 않는다. 분할점이 앞 이미지 안에 있어 한쪽 장면에 동영상 프레임이 없는 경우도 실제 Chromium MP4 비교를 통과했다. 음성은 원본 소스 구간을 나누고 프레임 경계의 오차를 별도 배치 오프셋으로 보정한다. 연속한 원본 녹음은 전체 미리보기와 MP4에서 한 구간으로 읽어 중간 페이드나 무음을 만들지 않으며, 분할 이후에만 시작하는 녹음도 원래 시간을 유지한다. 장면별 미리듣기·파형과 ZIP의 `narration.wav`는 해당 구간과 무음을 포함한 WAV로 준비하고 스테레오 채널을 유지한다. 온전한 원본 파일은 자료 목록과 ZIP에 그대로 남긴다.

실행 취소는 장면 추가·공통 장면 필드·핵심 업적 연결을 한 묶음으로 복원한다. 중첩 분할을 모두 취소한 동안에도 복원할 자식 장면의 이력을 보관한다. 뒤늦게 완료된 생성·업로드는 최신 장면 ID로 병합하고, 취소로 빠진 자식의 결과는 원본 목록에 보관하면서 다시 실행할 장면에도 반영한다. 새 녹음의 시간 조정에서는 화면 구간 이력과 녹음 연결을 따로 다뤄 취소·다시 실행으로 파일을 잃거나 길이를 잘못 복원하지 않는다. 분할 장면의 기존 전환·트림 조절은 구간 요약으로 표시하며 다른 화면 선택·이미지 효과·보조 이미지 선택·녹음 교체는 해당 장면에 적용한다.

분할한 프로젝트는 **편집 형식 4**와 `great100_save_structured_project`를 사용한다. 실행 취소 후에도 버전을 내리지 않으며 구형 저장 함수로 우회하지 않는다. 배포 전 [장면 나누기 SQL](../../supabase/migrations/202610200004_scene_splitting.sql)을 E의 SQL 뒤에 실행해야 한다. 첫 전환 전 사본은 계정의 `great100_structure_backups`, 로컬의 `editor-backup:<프로젝트 ID>:3`(직전 버전이 3인 경우), 데스크톱의 `project_data.pre-editor-v4.json`에 보관한다. 계정 이전도 형식 4와 분할 구간을 보존한다. 미리보기·음성 계산 변경에 맞춰 MP4 캐시 버전은 11로 올렸다.

검증은 **45개 파일의 257개 테스트와 운영 빌드**를 통과했다. 경계·최소 길이·겹치는 자막, 중첩 분할, 원본 구간·핵심 업적 연결, 긴 녹음 조정, 생성의 늦은 완료, 로컬 저장·재열기·사본·삭제, 계정 이전과 버전 4 RPC를 확인했다. PGlite에서 SQL 반복 적용·전환 사본 1회 보관·구형 RPC 차단·낙관적 충돌·원문과 원본 파일 불변·타 계정 격리와 사본 정리를 확인했다.

실제 Chromium에서는 4초 장면을 1.1초와 2.3초 자막 경계에서 중첩 분할하고 두 번의 취소·복원·재열기를 수행하고 개별 장면의 녹음 구간을 디코딩했다. 전체 검토와 완료 화면에서 만든 MP4는 **195프레임·13초**, AAC와 차이는 약 **0.0264초**였다. 분할 전후 디코딩한 화면 픽셀과 분할점 양쪽의 음성을 비교해 동영상·정지 화면·보조 이미지와 연속 음성의 일치를 확인했다. ZIP에는 원본 8개와 각 분할 장면의 WAV가 남았고 원본 녹음의 SHA-256과 원본 제작안이 일치했다. 페이지 오류는 0개였다. 기존 F1의 순서 변경·부분 음성 출력과 D의 긴 녹음 시간 조정·취소·저장·MP4·ZIP도 실제 브라우저에서 회귀 검증을 통과했다. 운영 Supabase/R2의 실제 쓰기와 패키징한 Tauri 앱은 검증하지 않았으며, 이 환경에 Cargo가 없어 네이티브 컴파일은 확인하지 못했다.

**F3의 인접 장면 합치기를 구현했다.** APP_DATA 2.1의 현재 장면에 다음 장면을 이어 붙인다. 대상 장면·합친 길이를 먼저 표시하며 두 화면을 선택하고 합계 120초 이하일 때 적용한다. 첫 장면의 고정 ID와 활성 선택을 유지하고 번호를 다시 매긴다. 자막 ID·문구·상대 시간, 두 장면의 원본 출처·이미지 후보·동영상·보조 이미지·녹음을 보존하고, 핵심 업적 연결을 첫 장면 ID로 옮긴다. 원문과 원본 JSON은 그대로 유지한다. 내부의 절대 시간 틈은 장면 길이의 합으로 정리하고 나머지 장면의 절대 시간은 유지한다.

F2의 원본 재생 시계 캡처를 공통 함수로 분리했다. 합치기 전에 각 화면의 동영상 트림·앞 이미지·보조 화면·정지 화면·효과 진행률을 보관하고 강조 문구·노출 나이·음악 볼륨도 구간마다 보관한다. 합친 뒤 밀리는 다른 장면의 자동 움직임도 기존 효과를 유지한다. 녹음에는 원래 장면의 프레임 종료 경계를 보관해 첫 장면의 반올림 잔여 시간이 두 번째 녹음에 섞이지 않도록 한다. 분할한 동일 녹음의 연속성은 계속 유지한다. 개별 장면 미리보기의 두 번째 화면 구간에 전체 영상 오프닝용 자막 페이드를 적용하던 조건도 바로잡았다.

합치기는 장면 제거·공통 필드·원본 출처·핵심 업적·후보 목록을 한 번에 되돌린다. 후보 목록은 ID에 따른 변경만 복원하므로 뒤늦게 도착한 업로드를 잃지 않는다. 제거될 두 번째 장면에 있던 이전 편집 이력도 유지하고, 진행 중이던 생성 결과는 합친 후보 목록과 보관 원본에 추가하며 취소에서 복원할 원래 장면에도 반영한다. 연속 합치기, 두 번의 취소·복원, 합친 뒤 재분할을 지원한다. 재분할한 뒤 장면의 기본 강조 문구·볼륨은 첫 보존 구간에 맞춘다. 강조·음악 설정 변경은 현재 장면 전체에 적용하고, 화면 교체는 현재 장면의 설정으로 전체 화면 구성을 교체한다.

구간별 표현과 녹음의 원래 재생 한계를 구버전 앱이 무시하지 못하도록 **편집 형식 5**와 `great100_save_merged_project`를 추가했다. 운영 배포 전에 [장면 합치기 SQL](../../supabase/migrations/202610200005_scene_merging.sql)을 F2 SQL 뒤에 적용해야 한다. 첫 전환 전 JSON은 계정의 `great100_merge_backups`, 로컬의 `editor-backup:<프로젝트 ID>:<직전 버전>`, 데스크톱의 `project_data.pre-editor-v5.json`에 한 번 보관한다. 형식 1~4의 기존 저장 계약은 유지하고 형식 5 요청은 이전 함수로 우회하지 않는다. 계정 이전에서도 구간별 강조·음악과 녹음 경계를 보존한다.

검증은 **46개 파일의 277개 테스트와 운영 빌드**를 통과했다. 합치기 전후 원본·핵심 업적·후보·효과·음성 시간, 내부 시간 틈, 소수 초, 합계 길이 제한, 합치기와 재분할, 이전 이력, 생성의 늦은 완료, 로컬 사본·재열기·삭제와 계정 이전을 검증했다. PGlite에서는 SQL 반복 적용, 첫 전환 사본, 원문·원본 자료 불변, 구형·타 계정 쓰기 차단, 충돌과 사본 정리를 확인했다.

실제 Chromium에서는 이미지·트림 동영상·보조 이미지와 서로 다른 WAV 녹음 두 개가 있는 세 장면을 3→2→1개로 합쳤다. 두 번의 취소·다시 실행, 재분할과 취소·복원, 저장·재열기, 개별·전체 미리보기와 실제 완료 화면의 MP4 생성을 수행했다. MP4는 **195프레임·13초**, AAC와 차이는 약 **0.0264초**였다. 합치기 전후 화면과 강조 문구·자막, 두 녹음을 디코딩해 비교하고 음악 볼륨 10%→85%→30%를 확인했다. 실제 렌더러의 인코딩 전 47·63·82·113번 프레임도 비교해 픽셀 차이가 0임을 확인했다. ZIP은 원본 10개, 세 화면·두 음성 구간과 합친 WAV를 보관했고 두 녹음 원본의 SHA-256과 원본 제작안이 일치했다. 페이지 오류는 0개였다. F2의 앞 이미지 내부 분할·중첩 나누기·취소·복원·재열기·MP4·ZIP도 실제 Chromium에서 회귀 검증했다. 운영 Supabase/R2의 실제 쓰기와 패키징한 Tauri 앱은 별도 검증 범위이며, 이 환경에는 Cargo가 없어 네이티브 컴파일을 확인하지 못했다.

**F의 순서 변경·나누기·합치기가 연결됐다.** 이후 작업은 G의 내레이션 자동화와 H의 전체 장면 검토·생성 큐다.
